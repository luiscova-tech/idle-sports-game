# CLAUDE.md — Idle Sports Franchise Builder

This file is read automatically at the start of every Claude Code session in this repo. Keep it current — see "Maintenance" at the bottom.

## Project Summary
A multi-sport idle/incremental franchise management game. Browser-first (React + Vite), with a planned later wrap for iOS via Capacitor. Full design brief: see `idle-sports-game-brief.md` in repo root.

## Tech Stack
- React + Vite (TypeScript template)
- Zustand for game state (single central store)
- react-router-dom for routing
- Client-side persistence only for v1 (localStorage/IndexedDB) — no backend
- 2D flat icon/sprite art for v1 (AI-generated, style-locked prompts)

## Architecture Principles
- **One shared engine, not per-sport systems.** Core engine (match sim, economy, player model, facilities, season/standings, prestige, events) is sport-agnostic. Sport-specific rules (stat weights, scoring, roster size) live in plugged-in sport modules.
- **Currency types are separated in the data model from day one** (even premium/future currency fields), so monetization can be added later without a rewrite.
- **v1 ships with exactly 2 sports.** Do not add a 3rd sport until the shared engine has been validated with 2 working end-to-end.
- Keep save/economy logic isolated in its own module — not scattered across UI components.

### Engine / sport-module split (established in step 2)
- `src/engine/types.ts` defines the sport-agnostic contract: `MatchOutcome` ('win'/'draw'/'loss'), `TickResult<TState>`, `MatchResult<TState>`, an optional `MatchContext` (`{level?, minWinLevel?}` — see "Match/economy escalation" below), and the `SportModule<TState>` interface (`id`, `ticksPerMatch`, `createInitialState()`, `tick(state, tickIndex, context?)`, `getOutcome(state, context?)`, `getPerformanceFactor(state, context?)`). `TState` is fully opaque to the engine — sport modules own their own state shape. `context` is optional everywhere it appears — a sport module free of any win-gating concept simply never reads it.
- `src/engine/tickEngine.ts` holds three pure, timer-free helper functions (`advanceTick`, `isMatchComplete`, `finalizeMatch`) that operate generically over any `SportModule<TState>`. It must never import from `src/sports/**` or reference sport-specific vocabulary. `advanceTick`/`finalizeMatch` both take an optional `context` and thread it straight through to whichever `SportModule` methods accept it — this file never inspects or interprets it.
- `src/engine/economy.ts` is the single isolated home for currency math — a `REVENUE_BY_OUTCOME` table keyed only on the generic `MatchOutcome`, shared by every sport rather than redefined per sport. `calculateMatchRevenue(outcome, performanceFactor)` additionally scales revenue by the sport module's generic 0-1 `performanceFactor` (see "Match/economy escalation" below) — this file only ever consumes that single generic number, never sport-specific stats.
- `src/engine/prestige.ts` is the single isolated home for prestige/Legacy Points math (see "Prestige system" below) — sport-agnostic, takes only a scalar "total earnings," never imports from `src/sports/**`.
- `src/engine/achievements.ts` is the single isolated home for the achievement/badge framework (see "Achievements" below) — sport-agnostic, consumes only a generic `Record<string, number>` stats record, never imports from `src/sports/**`.
- A sport plugs in by implementing `SportModule<TState>` in its own folder under `src/sports/<sport>/` (see `src/sports/soccer/soccerModule.ts`) — that's the only place sport-specific vocabulary (goals, possession, shots, etc.) is allowed to appear.
- The idle loop's `setInterval`s live in exactly one place — a React hook (`src/hooks/useMatchTicker.ts`). The engine, economy, and store stay fully timer-free and synchronously testable. As of the "Match/economy escalation" amendment below, the hook runs one independent interval PER auto-playing tier (real-world pacing is now a per-tier concern, via `autoTickIntervalMsForTier()`) rather than a single shared `intervalMs` parameter — see that section for why.
- The Zustand store (`src/store/useGameStore.ts`) instantiates one module-scoped sport module (currently `createSoccerModule()`), reused identically by every venture tier (see below) — never forked or reconfigured per tier.

### Manual-before-automated pattern (amendment to step 2)
Classic idle games hook players with manual interaction before automation is earned. Applied to soccer, and intended as the template for every future sport:
- A single per-tier resolution path (`tickTier(tierId)` in the store) advances that tier's match by one tick — it is called identically by the idle interval and by a manual player tap, so there is never a forked "manual" vs. "automatic" simulation branch.
- Each tier has its own `managerHired` boolean (default `false`) gating its own automation: `useMatchTicker` only auto-ticks tiers where `unlocked && managerHired` are both true. Before that, a tier only advances via its own manual "Push the Attack" button.
- `managerHired` is flipped by a one-time per-tier Revenue purchase (`hireManagerForTier(tierId)`, cost from that tier's config). This cost/unlock logic lives in the store/sport-module layer, not in `src/engine/economy.ts` — it's an idle mechanic ("pay currency to unlock automation"), not part of the sport-agnostic match-outcome economy.
- Chosen design: the manual action button stays visible and usable even after automation unlocks (a supplemental boost), rather than being hidden — matches the genre convention that active play keeps some value after idle progression is unlocked.
- Future sports should follow the same shape: a manual per-tick trigger wired to the same tick-resolution path, gated automation behind a purchasable unlock, no changes to `src/engine/**`.

### Venture tiers (second amendment to step 2 — Adventure-Capitalist-style restructuring)
The single global match view was replaced with a vertical stack of independent "venture tier" cards (`Local Game → Local Tournament → Regional Championship → National League → Continental Cup → World Championship → Legends' Circuit → Galactic League → Mythic Ascension → Eternal Championship → The Multiverse Cup` for soccer — tiers 5-6 added in the eighth amendment, tiers 7-11 added in the ninth amendment, the latter hidden until a player's first prestige), each its own parallel revenue generator:
- **Reuse vs. divergence:** every tier runs its match through the exact same `createSoccerModule()` instance and the exact same `advanceTick`/`isMatchComplete`/`finalizeMatch` (`src/engine/tickEngine.ts`) and `calculateMatchRevenue` (`src/engine/economy.ts`) — none of those files changed. The only per-tier divergence is a revenue multiplier (`baseRevenueMultiplier × level`) applied in the store, in `tickTier()`, on top of `economy.ts`'s base win/draw/loss payout. `economy.ts` itself has no concept of tiers.
- Tier names/multipliers/costs are sport-specific vocabulary, so they live in `src/sports/soccer/soccerModule.ts` (`SOCCER_VENTURE_TIERS`, `tierUpgradeCost()`) — the same file that owns "goal"/"chance"/etc. A second sport (step 3) defines its own tier list the same way.
- **Store shape:** `useGameStore.ts` now holds `tiers: VentureTier[]` (id, unlocked, level, managerHired, tickIndex, match, matchesCompleted, cumulativeRevenue, lastOutcome) instead of one global match object, plus the store-level actions `tickTier`, `upgradeTier` ("Improve Training" — raises `level`, cost grows per level via a mild exponential curve), and `hireManagerForTier`.
- ~~**Unlock-threshold logic chosen:** a locked tier unlocks once the immediately preceding tier's `cumulativeRevenue`... reaches a configured threshold, auto-checked every tick.~~ **Superseded** — see "Tier unlocking as a player purchase" below; unlocking is now a deliberate spend from the current Revenue balance, not an automatic threshold.
- Revenue stays ONE global currency (`currencies.revenue`), spent/earned by every tier — `cumulativeRevenue` is a per-tier informational stat (lifetime Revenue earned from that tier), not a second currency. This preserves the currency-separation principle above.
- UI: `src/components/VentureCard.tsx` (one per tier, mapped from the static `SOCCER_VENTURE_TIERS` config in `src/routes/Home.tsx`) replaced the old single `MatchPanel`/`MatchControls`, which were deleted. No styling pass yet (that's step 9) — just structure/interactivity.

### Payout visibility fix (third amendment to step 2)
Closed the "click with no feedback until match end" gap identified in playtesting: `VentureCard.tsx` now derives a live match-progress percentage (a native `<progress>` element) from `elapsedTicks / DEFAULT_SOCCER_CONFIG.ticksPerMatch`, and a live "if the match ended now" projected-payout line. The projection reuses `getOutcome()` (now exported from `soccerModule.ts`) and `calculateMatchRevenue()` (`src/engine/economy.ts`) — the exact same functions the store calls at real match completion — so the preview can never drift out of sync with the actual payout. Purely presentational at the time it was made; superseded below by an actual economy change (Revenue is no longer only credited at completion).

### Persistence (transparent addition to step 2)
`src/store/useGameStore.ts` is now wrapped in zustand's `persist` middleware (localStorage, key `idle-sports-game-save`), per the "client-side persistence for v1" tech-stack line. `partialize` persists only `{ tiers, currencies }` — actions are always recreated fresh, never serialized. This is transparent to every tier/economy/engine call site above; none of that code changed.

### Direct-click economy model (fourth amendment to step 2 — supersedes "pay at outcome only")
Manual clicks (and equivalently automated ticks — same `tickTier()` path, no fork) now grant direct, immediate Revenue every tick. The match-completion payout is no longer the only source of Revenue; it's an additional bonus stacked on top:
- `src/sports/soccer/soccerModule.ts` adds `BASE_PER_TICK_REVENUE = 4` and `tierPerTickRevenue(config, level)` (`round(BASE_PER_TICK_REVENUE * baseRevenueMultiplier * level)`) to its additive tier-config section — the same scaling factor the completion bonus already uses, so relative tier/level progression stays consistent between the two income sources. `tick()`, `getOutcome()`, `DEFAULT_SOCCER_CONFIG`, and `createSoccerModule()` are unchanged.
- `tickTier()` in the store now adds `perTickRevenue` to both `currencies.revenue` and that tier's `cumulativeRevenue` on **every** tick, not only at completion. On the completion tick, the unchanged completion-bonus formula is added on top (`totalEarned = perTickRevenue + completionBonus`), never replacing it. (`cumulativeRevenue` still accrues every tick as a per-tier informational stat, but — as of the fifth amendment below — no longer drives unlocking.)
- **Balancing reasoning:** assumed 1 click/sec (a conservative, easily-sustained manual pace, slower than the game's own 600ms auto-tick rate). At `BASE_PER_TICK_REVENUE=4`, Local Game/level 1 earns 4 Revenue/tick, so the cheapest first purchase (Improve Training, cost 100) is reachable in `100/4 = 25` ticks ≈ 25s — the middle of the requested 20-30s window.
- **Threshold numbers chosen (originally as auto-unlock thresholds, now reused as unlock purchase costs — see below):** `local-tournament` 600→450, `regional-championship` 3000→2250, `national-league` 15000→11250 (`local-game`'s is unused). The 450→2250→11250 ladder is a clean 5x/5x growth, preserving the pre-existing design intent that unlock costs compound faster than the (unchanged, ~4x/3x/2.9x) multiplier growth per tier.
- UI: both purchase buttons show a clamped "current/cost Revenue" progress format (e.g. `Improve Training (72/100 Revenue)`, capped at the cost once affordable) instead of a flat cost, and a `+N Revenue per push` caption sits under "Push the Attack", computed via the same `tierPerTickRevenue()` helper `tickTier()` uses — never a separate hardcoded number.
- Playtested end-to-end: first Revenue is now visible after exactly one click (previously required a full 90-tick match); the first affordable purchase (Improve Training) now lands at click/second 25 (previously took multiple full matches, hundreds of clicks).

### Tier unlocking as a player purchase (fifth amendment to step 2 — supersedes automatic threshold-unlock)
Unlocking a tier is now a deliberate spend, not something that fires automatically once a stat crosses a threshold:
- `SoccerVentureTierConfig`'s `unlockThreshold` field is renamed `unlockCost` — it's paid from the player's current spendable `currencies.revenue` balance, the exact same pool `upgradeTier`/`hireManagerForTier` draw from. The three cost values are unchanged (450 / 2250 / 11250) — only the trigger mechanism changed, per this amendment's request.
- New store action `unlockTier(tierId)`: no-op if already unlocked or Revenue is insufficient; otherwise deducts `unlockCost` and flips that tier's `unlocked` to `true`. Same shape as `upgradeTier`/`hireManagerForTier` — no new pattern introduced.
- `applyTierUnlocks` (the old every-tick auto-check function) is deleted entirely — `tickTier()` no longer touches unlock state at all, only match/revenue state.
- UI: a locked tier's card now shows an always-rendered "Unlock {name} ({current}/{cost} Revenue)" button, disabled until affordable — identical pattern to the Improve Training/Hire a Manager buttons, rather than a passive progress readout.
- **This is the intended design:** because unlock cost is drawn from the same balance as every other purchase, spending on the current tier directly delays affording the next tier's unlock, and vice versa — a real, felt trade-off, not just numbers on two independent tracks. Playtested and confirmed: buying Local Game's "Improve Training" at Revenue=100 visibly reset "Unlock Local Tournament" progress from 100/450 back to 0/450 in the same instant; later, spending 450 to unlock Local Tournament at Revenue=456 instantly dropped Local Game's own Improve Training/Hire a Manager buttons from affordable back to disabled. Both directions of the tension are directly observable, not theoretical.

### Reset Progress button (seventh amendment to step 2)

- New store action `resetProgress()` in `useGameStore.ts`: sets `tiers` back to `createInitialTiers()` and `currencies` back to `{ revenue: 0 }`. Guarded by a native `window.confirm()` before calling `resetProgress()` — cheap, no new dependency, prevents an accidental misclick from wiping progress.
- Verified: reset correctly zeroes all tiers/currencies and rewrites the `localStorage` entry; canceling the confirm dialog leaves progress untouched.

### Prestige system: "Reset for Legacy" (step 7 — new architectural layer, not a tier extension)
Adventure-Capitalist-style prestige: trade this run's progress for a small, permanent currency and a handful of lasting upgrades. Deliberately built as its own layer (`src/engine/prestige.ts` + `LegacyState` in the store + `LegacyPanel.tsx`), not bolted onto the venture-tier code — tiers/economy/engine files from steps 1-2 above are unchanged by this step.
- **Trigger:** `resetForLegacy()` (`src/store/useGameStore.ts`) is a no-op unless `FIRST_PRESTIGE_TRIGGER_TIER_ID` (`'world-championship'`, exported from `soccerModule.ts`) is unlocked. The UI (`LegacyPanel.tsx`) shows a locked explainer until then, matching the venture-tier lock-card convention rather than hiding the system outright. ~~Originally checked by array position (`tiers[tiers.length - 1].unlocked`), reasoned to "stay correct if the ladder grows."~~ **That reasoning was wrong** — see the ninth amendment below, which appended 5 more tiers and broke this exact assumption; the trigger is now looked up by id specifically, not by position.
- **Legacy Points formula:** `calculateLegacyPoints(totalEarnings) = floor(sqrt(totalEarnings) / 10)` (`src/engine/prestige.ts`), where `totalEarnings` is the sum of every tier's `cumulativeRevenue` since game start or the last reset. Square-root scaling means early revenue counts for more per-point than the huge late-game numbers, so points keep climbing (not stalling) across repeated future prestiges.
  - **Constant derivation:** simulated a greedy "always spend on the most useful thing" playthrough of the real soccer ladder (unlock next tier > hire manager > buy training, in that priority, against 1.667 auto-ticks/sec once a manager's hired + 1 manual click/sec on the frontier tier) to estimate realistic total lifetime earnings at the moment a player first unlocks World Championship. Three scenarios: no managers/no upgrades (mathematical floor, ≈352k, ~59 LP), managers-but-no-upgrades (≈429k, ~65 LP), managers-and-upgrades (≈990k, ~99 LP). Picked the scaling constant `10` so this whole realistic range maps to **~59-99 Legacy Points** on a first prestige — enough to buy 1-2 of the cheaper permanent upgrades below, not the whole tree, matching the "meaningful but not trivializing" brief.
  - The live "Reset for Legacy" preview in `LegacyPanel.tsx` calls the exact same `calculateLegacyPoints()` the store's `resetForLegacy()` uses — same drift-proof preview pattern as the third amendment's match-payout projection above.
- **On confirming reset:** `resetForLegacy()` adds the computed Legacy Points to `legacy.legacyPoints`, sets `legacy.hasPrestiged = true` and increments `legacy.prestigeCount`, then rebuilds `tiers`/`currencies` via the same `createInitialTiers()`/`startingRevenue()` helpers a brand-new game uses (parameterized by the *current* permanent upgrades — see below). `legacy.legacyPoints`/`hasPrestiged`/`prestigeCount`/`permanentUpgrades` are never touched by this reset. `hasPrestiged` gates tiers 7-11's existence in the UI — see the ninth amendment below.
- **Permanent upgrade tree** (`PERMANENT_UPGRADES` in `src/engine/prestige.ts`, purchased via `purchaseLegacyUpgrade()`), kept to 4 small effects expressed generically (a revenue multiplier, a starting-capital amount, a pre-unlocked-tier count, an unlock-cost discount) so a second sport's ladder benefits with zero changes here:
  - ~~**Revenue Boost** — +10% global Revenue (per-tick and completion) per level, 5 levels, cost `20 × level` LP (20/40/60/80/100).~~ **The 5-level cap was removed** in the thirteenth amendment (Block B) — now scales indefinitely, same cost formula. Applied in `tickTier()`/`VentureCard.tsx` via `globalRevenueMultiplier()`.
  - **Head Start Capital** — one-time, 15 LP: every future run starts with 500 Revenue already banked (`startingRevenue()`).
  - **Fast Track** — one-time, 40 LP: Local Tournament starts pre-unlocked on every future run (`startingUnlockedTierCount()`).
  - ~~**Veteran Discount** — -5% to every tier's unlock cost per level, 3 levels, cost `35 × level` LP (35/70/105). Fully maxing all four costs 565 LP total — a long-term, many-prestiges goal, not a first-run one.~~ **The 3-level cap was removed** in the thirteenth amendment (Block B) — now scales indefinitely toward a 75%-off asymptote that can never be reached. Applied in `unlockTier()`/`VentureCard.tsx` via `unlockCostMultiplier()`.
  - All four are additive/no-op with zero owned (levels 0/false) so a player who never prestiges sees byte-for-byte the same behavior as before this step.
- **UI:** `src/components/LegacyPanel.tsx` + `LegacyPanel.css`, rendered above the venture-tier list in `Home.tsx`. Deliberately a different hue family (`--color-legacy*` purple/gold tokens in `index.css`, light + dark) from the tier cards' blue/green/amber, so it reads as a distinct currency/system at a glance. The reset button is guarded by a native `window.confirm()` detailing the Legacy Points about to be gained and what gets wiped — same cheap, no-new-dependency pattern as the existing Reset Progress button (seventh amendment above), appropriate given this is also a destructive-to-run-progress action.
- **Distinct from the existing "Reset Progress" debug button:** that button (`resetProgress()`) is a full wipe INCLUDING Legacy — it now also resets `legacy` back to `createInitialLegacy()`, so it stays a true "brand new player" reset rather than a confusing half-reset. `resetForLegacy()` is the only path that preserves Legacy Points/upgrades.
- **Playtested first-prestige walkthrough (the actual test of whether this works):** seeded a run with 700,000 total earnings (mid-point of the simulated range) and unlocked World Championship → preview correctly showed "83 Legacy Points" → confirmed reset → tiers/Revenue wiped to fresh-game state, `legacyPoints` became 83. Spent 20 LP on Revenue Boost lvl 1 + 15 LP on Head Start Capital (35 of 83 spent, 48 banked for next time) and separately verified Fast Track. Starting a new run afterward: Revenue began at 500 (vs. 0) and Local Tournament was already unlocked (vs. requiring a 450-Revenue grind) — both immediately felt, real head-starts — while Regional Championship onward still require the same near-full unlock grind as a first run, just ~10% faster forever from Revenue Boost and (if Veteran Discount is later bought) slightly cheaper unlocks. This is exactly the intended shape: a felt boost to the early game, not a skip of the whole run.
- Verified: build/lint clean; exercised `resetForLegacy`, all 4 `purchaseLegacyUpgrade` branches, and `resetProgress`'s full-wipe-including-Legacy behavior directly against `localStorage` state in the browser preview (native `confirm()` dialogs are auto-suppressed in the preview tool's automation, so purchase/reset actions were confirmed by patching `window.confirm` for verification purposes only — real players get the normal browser dialog). Caught and fixed one real bug during this verification: `VentureCard.tsx`'s locked-tier unlock-cost display and the unlocked-tier per-tick/projected-payout previews were reading raw `soccerModule.ts` config numbers and hadn't been updated to apply the new Legacy multipliers, so they'd have drifted from what the store actually charged/granted once any Revenue Boost or Veteran Discount was owned — fixed by routing all three through the same `globalRevenueMultiplier()`/`unlockCostMultiplier()` helpers the store uses.

### Achievements: generic badge framework (eleventh amendment to step 2 — new system, not a tier/prestige extension)
A third meta-system, deliberately architected as its own layer (`src/engine/achievements.ts` + `LifetimeStats`/`AchievementsState` in the store + `AchievementsPanel.tsx`) — no changes to tiers/economy/prestige files.
- **Framework:** `AchievementConfig = {id, name, statTracked, threshold, tier, reward}`, where `statTracked` is a plain string key into a `Record<string, number>` stats record (not an enum), and `tier` is a plain string rather than a closed union — deliberately so a future achievement line or a 4th badge tier (e.g. "Platinum") never requires widening a type here, only adding data. `reward.type` IS a closed union (`'revenue' | 'legacyPoints'`, only two reward kinds exist by design), but every place that branches on it (`useGameStore.ts`'s reward loop, `AchievementsPanel.tsx`'s `rewardLabel`) uses an exhaustive `switch` ending in `assertNeverRewardType()` — so adding a third reward kind without updating both is a compile error, not a silently-wrong-currency-granted bug. `checkNewlyEarnedAchievements(stats, earnedIds)` is pure: it returns which not-yet-earned `ACHIEVEMENTS` now qualify, applies no rewards, mutates nothing — the store is solely responsible for granting.
- **First achievement line — total wins across every venture tier combined (not per-tier):** Bronze 50 wins → +200 Revenue; Silver 250 wins → +2000 Revenue; Gold 1000 wins → +10 Legacy Points.
  - **Threshold derivation:** simulated the same greedy always-be-spending policy used to tune Legacy Points (unlock next tier > hire manager > train), this time tracking wins, using an empirically-measured ~53% per-match win rate (simulated 200k matches against the actual tick probabilities). Under that hyper-engaged model: 50 wins ≈ 15.6 min, 250 wins ≈ 67 min, 1000 wins ≈ 260 min (~4.3 hours). A 50→250→1000 ladder is a clean 5x/4x escalation, matching the ratio style already used for tier costs elsewhere in this file. Real, less-than-maximally-optimized play takes meaningfully longer at every threshold — intentional: Bronze is "your first solid session," Silver is "you're invested," Gold is "hours of real cumulative play," not literal-minutes milestones.
  - **Reward derivation:** Bronze/Silver deliberately stay small relative to the same currency they're paid in (200/2000 Revenue vs. contemporaneous unlock costs of 450/11250+) — a nudge, not a shortcut. Gold pays in Legacy Points instead of Revenue specifically to bridge the two currency systems: 10 LP is enough to almost afford Head Start Capital (15 LP) outright, giving even a player who hasn't prestiged yet a first taste of the permanent currency.
  - **Scope decision, documented rather than left silent:** an achievement's Revenue reward lands directly in `currencies.revenue` (spendable immediately) but is NOT added to any tier's `cumulativeRevenue`, so it does not count toward that run's eventual Legacy Points at prestige (`resetForLegacy()` sums only `tiers[].cumulativeRevenue`). This is consistent with `cumulativeRevenue`'s documented per-tier semantics (an achievement is a cross-tier, lifetime accomplishment, not attributable to the one tier whose match happened to trigger it) — but it is a deliberate boundary, not an oversight: two players with identical tier progress will get identical Legacy Points on prestige even if one of them also banked a Bronze/Silver achievement along the way.
- **Lifetime, not per-run:** `lifetimeStats.totalWins` and `achievements.earnedIds` (`useGameStore.ts`) live outside `tiers`/`legacy.permanentUpgrades`, with the exact same persistence semantics as `legacy.legacyPoints`/`hasPrestiged` — never reset by `resetForLegacy()` (an achievement is a lifetime accomplishment; wiping badge progress on every prestige would be actively punishing, not motivating), only by the full `resetProgress()` dev wipe. Deliberate, not the only option available: per-tier `cumulativeRevenue`/`matchesCompleted` ARE reset every prestige despite their own "lifetime" doc comments — but a badge system specifically needs badges to stay earned.
- **Granting is atomic and runs on every tick, not just match completions:** a shared `applyEarnedAchievements()` helper is called from BOTH of `tickTier()`'s branches — the match-completion branch (where `totalWins` actually changes) AND the plain per-tick branch (where it currently doesn't). This was a deliberate fix during review: the first draft only checked achievements at completion, which happened to work for a completion-only stat like wins, but would have silently under-served the framework's own documented example of a future line ("total Revenue earned") — Revenue changes on *every* tick, not just at completion, so an achievement-check wired into only one branch would leave such a threshold unrecognized for up to `ticksPerMatch` ticks after it's actually crossed. Both branches now call the same generic check symmetrically, so a future per-tick stat is caught immediately. Each call applies every newly-earned reward (to `currencies.revenue` and/or `legacy.legacyPoints`) within the same `set()`, so the UI never renders a frame where a badge shows earned but its reward hasn't landed. Correctly handles multiple simultaneous grants (e.g. a hand-edited save jumping straight past all three thresholds in one tick earns all three at once, with all three rewards applied).
- **Extending this later — honestly scoped:** a new achievement line (total Revenue earned, matches played, prestige count, ...) is *mostly* config: new entries in `ACHIEVEMENTS`/`STAT_LABELS` in `achievements.ts`. Being precise rather than overselling it: a genuinely new tracked stat still needs its own field + increment site(s) (in `LifetimeStats` if it must survive prestige, exactly like `totalWins`) plus one line in `AchievementsPanel.tsx`'s `stats` record mapping that field to the key `statTracked` expects — that plumbing is unavoidable since the stat has to be tracked somewhere, and an adversarial review specifically flagged the earlier "just add config" framing as stronger than what the code actually delivers. `prestigeCount` is a rare exception needing *none* of that extra wiring, since it already lives in `legacy.prestigeCount` with the right lifetime persistence — a "reached N prestiges" line really would be pure config.
- **UI:** `src/components/AchievementsPanel.tsx` + `.css`, rendered in `Home.tsx` between `LegacyPanel` and the venture-tier list. A third distinct hue (cyan, `--color-achievement*` in `index.css`) from both the tier cards and Legacy's purple/gold — shifted from an initial teal after review flagged it as only ~19° of hue apart from `--color-success` (too close to read as clearly distinct); cyan sits a safer ~37° away. Individual badge chips use conventional bronze/silver/gold swatches (`--color-badge-*`); silver was likewise reworked from a near-identical match to `--color-text-muted` into a distinctly cooler, lighter steel-blue. An explicit cyan fallback (`.achievement-badge--other`) styles any future tier name outside those three, so "extensible beyond Bronze/Silver/Gold" holds visually, not just in the type system. Achievements are grouped by `statTracked`, so a second line just adds a second group with zero changes to the grouping logic.
- **Playtested honestly — does this add anything in a new player's first few minutes?** Manually clicked "Push the Attack" ~38 times to afford Local Game's first manager hire (~1-2 minutes of realistic new-player clicking), then let it auto-tick for roughly 4 more real minutes total. Result: **2 of 50 wins** — a small but genuinely-moving, non-zero progress bar, exactly in line with the ~15.6-minute Bronze estimate above (a single-tier, non-hyper-optimized player is slower than the multi-tier greedy simulation). Honest verdict: it does **not** feel empty or ignorable — all three badge tiers, their thresholds, and their concrete rewards are visible and legible from the very first render, and the Gold tier's "+10 Legacy Points" line quietly foreshadows the whole prestige system before a player has even unlocked it. But Bronze is genuinely **not** a first-few-minutes payoff for a normal (non-optimized, single-manager) player — it's closer to a first-session milestone. If a snappier "hooked in five minutes" moment is wanted later, the right fix is a *separate* achievement line with a much lower entry threshold (e.g. "first win," or "10 wins") — not lowering this line's Bronze to something below 50, which is calibrated as this line's real entry point, not the game's.
- **Verified:** build/lint clean. An adversarial code-review workflow (4 dimensions, 24 agents including verification) raised 21 findings and confirmed 11 as real; all medium/high-severity ones were fixed (the completion-only achievement check, the non-exhaustive reward-type branching, the Silver/teal color collisions) as detailed above; the low-severity ones (the cumulativeRevenue scope decision, this section itself being newly written) are addressed by documentation rather than code, per their own "plausibly intentional"/"expected, not yet done" framing. Re-verified reward-granting/reset semantics after the fixes via an isolated Node harness importing the real store module directly (same technique as the tiers 7-11 session): crossing 50 wins grants Bronze exactly once, with no double-grant on a subsequent non-completion tick; jumping straight to 1000 wins grants all three tiers simultaneously with exactly correct amounts (+200 and +2000 Revenue, +10 Legacy Points); `resetForLegacy()` leaves `lifetimeStats`/`achievements` completely untouched across a prestige; `resetProgress()` correctly wipes both to zero/empty. ### Prestige reveal cadence, uncapped Legacy sinks, training-gated match escalation, and milestone multipliers (thirteenth amendment to step 2)
Four related balance/pacing changes agreed on in design discussion, done together in one session because they interact (per-tier training level, in particular, is now touched by three of the four). No build-order step changed — this is entirely within step 2's existing systems (venture tiers, prestige, achievements were all already done).

**Block A — one hidden tier revealed per prestige, not all 5 at once.** Superseded the ninth amendment's "`hasPrestiged` reveals all of tiers 7-11 together":
- `revealedTierCount(prestigeCount)` (`soccerModule.ts`, replaces `TIERS_REVEALED_BEFORE_PRESTIGE`) = `TIERS_REVEALED_AT_START` (6) + `min(prestigeCount, MAX_POST_PRESTIGE_REVEALS)` (5) — tier 7 (`legends-circuit`) reveals after prestige #1, tier 8 after #2, ... tier 11 after #5, and reveals stop there (a 6th+ prestige only earns more Legacy Points, reveals nothing new). `isTierRevealed(tierIndex, prestigeCount)` takes the count directly now, not the old boolean — every call site in `useGameStore.ts` (`tickTier`/`upgradeTier`/`hireManagerForTier`/`unlockTier`) and `Home.tsx`'s render slice was updated to pass `legacy.prestigeCount`.
- No minimum time/earnings gate between prestiges, per instruction — a player rushing through resets quickly reveals tiers just as fast; that's an accepted trade-off (they're also giving up more mid-run progress each time), not something worth adding friction to prevent.
- `LegacyPanel.tsx` copy now names the *specific* next tier ("Prestiging again will permanently reveal The Legends' Gauntlet (4 more tiers to reveal after that)") instead of implying a single all-at-once unlock, both in the locked-explainer text and the reset-confirmation dialog.
- **`hasPrestiged` still exists** (gates the Legacy panel's locked-vs-reset-block UI) but no longer drives the reveal boundary — `legacy.prestigeCount` does. Both are lifetime fields, never reset by `resetForLegacy()`, only by `resetProgress()`'s full wipe.
- **Save-compatibility note, deliberate not a bug:** any save that already had `prestigeCount >= 1` under the OLD "reveal all 5" rule will, after this change, only see `revealedTierCount(prestigeCount)` tiers (e.g. a save with `prestigeCount: 1` now sees only tier 7, not all of 7-11). Any tiers 8-11 state that save already had (level/unlocked/cumulativeRevenue) is NOT deleted — it just becomes inert/hidden again until later prestiges re-reveal it — and gets wiped on the save's next prestige regardless, same as any tier's progress always has. This is the correct, intended consequence of the requested rule change (there is no way to "reveal exactly one tier per prestige" without an existing multi-prestige save's visible count changing to match), not something migration code should paper over.

**Block B — Revenue Boost and Veteran Discount scale indefinitely (`prestige.ts`).** `maxLevel` removed from both; `PERMANENT_UPGRADES.revenueBoost`/`veteranDiscount` no longer have the field, and `purchaseLegacyUpgrade()`/`LegacyPanel.tsx` no longer check or render a "MAXED" state for either (Head Start Capital/Fast Track are unchanged one-time toggles).
- **Revenue Boost:** cost formula unchanged (`20 × nextLevel` — already a valid indefinite-scaling formula, just previously artificially capped at level 5). This is an economic soft cap by design: technically infinite, practically self-limiting because cost keeps climbing every level forever while the benefit stays a flat +10%/level.
- **Veteran Discount — required a genuine mathematical asymptote, not just a soft cap, since a 100% discount would make unlocking free and break the economy:** `unlockCostMultiplier(level) = (1 - MAX) + MAX × RATE^level`, with `MAX = 0.75` (asymptote: never more than 75% off) and `RATE = 0.9` (each level closes 10% of the *remaining* gap to that asymptote, not 10% of the original cost). The discount is `MAX × (1 - RATE^level)`. This is safe by construction, not by floating-point luck: the multiplier is `floor + MAX × RATE^level` where `floor = 1 - MAX = 0.25` is added as its own fixed term, so even if `RATE^level` underflows to exactly `0.0` at extreme levels (verified via harness: happens by level ~15,000), the multiplier still evaluates to exactly `0.25`, never below it — the 100%-discount case is structurally unreachable, not merely improbable. Verified: multiplier stays `> 0.25` at level 100, `== 0.25` (the floor, not below) at levels 100,000 and 1,000,000.
- Cost formula also unchanged (`35 × nextLevel`) — the asymptote's own diminishing returns are what keeps very high levels not worth grinding for, so cost doesn't additionally need to gatekeep it.

**Block C — three related match/economy changes, all through the `SportModule<TState>` engine contract:**
1. **Per-tier auto-play timing.** Match length stays a fixed 90 ticks at every tier (unchanged) — only the REAL-WORLD milliseconds between auto-ticks now varies per tier: `autoTickIntervalMsForTier(tierIndex) = round(600 × 1.4^tierIndex)` (`soccerModule.ts`), tier 0 unchanged at 600ms (~54s/auto-match) climbing to ~17.4s at tier 10 (~26min/auto-match) — a ~29x spread. Manual "Push the Attack" clicks never go through this at all (they call `tickTier()` directly from `VentureCard.tsx`), so hand-grinding a high tier is never slowed by this. `useMatchTicker.ts` was rewritten to run one independent `setInterval` PER auto-playing tier at its own pace, rather than one shared interval — see the bug/fix note below for why that rewrite mattered.
2. **Margin-based bonus revenue via a generic "performance factor."** `SportModule<TState>` gained a required `getPerformanceFactor(state, context?): number`, returning a generic 0-1 scale (0 = most lopsided possible loss, 0.5 = neutral/any real draw, 1 = most decisive possible win) — `economy.ts`'s `calculateMatchRevenue(outcome, performanceFactor)` only ever consumes that number, never sport-specific stats. Soccer derives it from clamped goal differential (`MAX_MEANINGFUL_GOAL_DIFFERENTIAL = 5`, simulated: P(|diff|≥5) ≈ 3.2% of matches — a real but genuinely rare blowout tail). The bonus (`decisiveness = max(0, (factor-0.5)×2)`, revenue `= base × (1 + 0.6 × decisiveness)`) only ever applies ABOVE neutral and only ever adds on top of the flat base — a decisive win pays more, but no outcome is ever paid LESS than its own flat base, specifically so there's never a "lose more decisively for more Revenue" exploit. A minimum win (1-0) pays ~+12%, a blowout (5+) pays +60%.
3. **Minimum training level to win.** `MatchContext` (`types.ts`, `{level?, minWinLevel?}`) is an optional capability threaded through `tick()`/`getOutcome()`/`getPerformanceFactor()` — a sport module with no such concept just never reads it, and the engine (`tickEngine.ts`) never interprets it, only passes it through. Soccer's `getOutcome()` downgrades a would-be 'win' to 'draw' outright (hard cliff, not a scaled-down chance) whenever `level < minWinLevel`; `minWinLevelForTier(tierIndex) = tierIndex + 1` (1 for tier 0 — no gating — up to 11 for The Multiverse Cup). Simulated against the real per-tier cost/revenue curves rather than guessed: a linear +1/tier keeps every tier's first-ever win within single-digit minutes of dedicated manual play at low tiers and a genuine-but-never-impossible few-hours-to-low-days at the top tier; steeper escalation (e.g. doubling per tier) was tried and rejected in simulation because this economy's exponential per-level training cost makes even level ~20-30 already many-days-to-unreachable at the top tiers, which would make a top tier's win outcome permanently impossible — the opposite of the intent.

**Block D — compounding-doubling training milestones (`soccerModule.ts`).** `trainingEffectMultiplier(level) = level × 2^(milestones passed)`, milestones at `TRAINING_MILESTONE_LEVELS = [6, 13, 22, 34, 50, 70, 95, 125, 160, 200]` (widening gaps: 7, 9, 12, 16, 20, 25, 30, 35, 40) — used everywhere a tier's level scales revenue (`tierPerTickRevenue()`, and the store's/`VentureCard.tsx`'s completion-bonus formulas, replacing the old raw `× level`). Does NOT affect `tierUpgradeCost`, which stays keyed on raw level exactly as before — only the revenue side gets the milestone boost.
- **Thresholds are simulated, not round numbers:** without any milestone boost, this economy's exponential `upgradeCostGrowth` (1.6-2.05× per level) against linear-in-level revenue means the level-up cadence itself grows roughly `g` times slower every additional level, so a fixed absolute level becomes many-days-then-effectively-unreachable within a few dozen levels at EVERY tier (confirmed: reaching level 30 baseline takes ~12.6 days at tier 0, and levels beyond ~25-30 are already outside a 58-day simulation cap at every tier tried) — regardless of a tier's own `baseRevenueMultiplier`, since that only shifts the wall by a roughly-constant number of levels against an exponential, never removes it. A first search tried [10, 25, 50, 100, 200, ...] and failed immediately in simulation (the 10→25 gap alone already cost 17+ hours even with the first doubling active) — the shipped thresholds were tightened until the first several milestones landed within single-digit minutes to about an hour of dedicated single-tier training investment at any tier, matching this session's "first breakpoint fairly early" ask; by design (matching Cookie Clicker's own high-count building milestones widening from every-few to every-50), the later ones (125+) are intentionally long-horizon, many-real-days goals for only the most dedicated single-tier grinding.

**Adversarial review and fixes.** A workflow-based review (6 interaction-focused lenses × adversarial verification, 28 agents total) specifically hunting for cross-block interaction bugs raised 11 candidate findings and confirmed 9; the following were fixed:
- **Root-cause bug, independently flagged by 5 of the 6 lenses:** `getPerformanceFactor()` didn't take `context`, so a `getOutcome()`-downgraded win (Block C3, label now `'draw'`) still reported its real, non-neutral goal-differential factor to `getPerformanceFactor()`, letting Block C2's margin bonus leak into what was paid out as a flat draw — e.g. a 2-0 downgraded win paid 50 Revenue instead of the intended flat 40 (a 25% overpay that scales with tier/level/Legacy Revenue Boost, and inflates `cumulativeRevenue` feeding Legacy Point math). Fixed by giving `getPerformanceFactor()` the same optional `context` parameter as `getOutcome()` (both now share a private `isGatedWin()` check in `soccerModule.ts`, so the two can't drift apart again) — a gated win now reports exactly the neutral `0.5` a genuine draw would. `VentureCard.tsx`'s preview was updated to pass the same context to both calls.
- **`useMatchTicker.ts` interval-starvation bug:** the original per-tier-interval rewrite still tore down and recreated ALL auto-tier intervals whenever the SET of auto-playing tiers changed at all (e.g. hiring a manager for a brand-new low tier). With tiers now at wildly different real-world intervals (600ms to ~17s), this meant a high tier's long-running countdown could be perpetually reset to zero before ever firing, if managers were hired often enough elsewhere. Fixed by diffing against a `useRef` map of tier-id → interval-id and only adding/removing the tiers that actually entered/left the auto-playing set — an unrelated tier's timer is never touched.
- **`LegacyPanel.tsx` off-by-one:** the "N more tiers to reveal after that" count used `legacy.prestigeCount` as-is, but that hasn't incremented yet for the prestige the copy is describing ("prestiging again will reveal X") — it was counting the very tier about to be revealed as still remaining. Fixed to count against `prestigeCount + 1`; also fixed grammar (singular "tier" vs plural "tiers").
- **Reset-for-Legacy dialog clarity:** didn't call out that every tier's training level (not just Revenue/unlocks) resets, which — new as of Block C3 — means wins at previously-trained tiers may resolve as draws again post-reset until retrained. Added a clause to the confirmation text.
- One additional candidate (whether `useMatchTicker`'s auto-tier filter needed its own `isTierRevealed` check) was correctly refuted on verification: `tickTier()` already no-ops for an unrevealed tier as its own defense-in-depth guard (per the ninth amendment), so a phantom interval for a hidden tier would tick nothing, not a real bug.

**Conceptual playtest across all four systems together.** Simulated a greedy (unlock-next > hire-manager > train) single-frontier-tier policy across 6 successive prestiges, spending Legacy Points greedily (Head Start Capital > Fast Track > cheapest of Revenue Boost/Veteran Discount) each time: time-to-reach-World-Crown decreased smoothly run over run (relative pacing units: 8.4 → 6.0 → 5.5 → 5.3 → 5.3 → 4.9) while per-run Legacy Point income stayed roughly flat (~94-104 LP) — a healthy diminishing-returns curve, not a stall (numbers never plateau-then-jump) or a runaway snowball (Revenue Boost's linear-cost/flat-benefit shape and the LP formula's own sqrt-scaling both damp the loop). Combined with Block A's reveal cadence, this means each successive prestige both reveals a new tier AND makes reaching World Crown again modestly faster — matching the "a lot more of the same game, not a brick wall" verdict the ninth amendment already reached for the tiers 7-11 climb itself.
- Verified: build/lint clean; a direct-import Node harness (same technique as prior sessions) covers all four blocks plus the specific regression the adversarial review caught (gated win reports factor `0.5` and pays exactly the flat draw rate, not an inflated one).

## Conventions
- Scoped sessions: work one build-order step at a time. Stop and summarize before starting the next step unless explicitly told to continue.
- Prefer clarity/maintainability over premature optimization — this is a solo long-term project, not a performance-critical app.
- Solo git workflow: commit directly to `main` for all build-order steps. Do not create feature branches or open pull requests unless explicitly asked.
- End-of-session deliverables: every session ends with (1) a written summary of what was done, (2) a plain-text description of the current UI state as observed via the browser preview tool (what's rendered, what changed visually) — even without a screenshot, so the user can relay it to another reviewer — and (3) a playable link left running (start/restart the dev server via the browser preview tool, clear `localStorage` for a fresh-player state, then give the `http://localhost:5173` URL — noting it's local-only and stops when the session ends). Don't stop the server as a "cleanup" step; leave it running and reset instead.
