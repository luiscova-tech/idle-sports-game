# CLAUDE.md — Idle Sports Franchise Builder

This file is read automatically at the start of every Claude Code session in this repo. Keep it current — see "Maintenance" at the bottom.

## Project Summary
A multi-sport idle/incremental franchise management game. Browser-first (React + Vite), with a planned later wrap for iOS via Capacitor. Full design brief: see `idle-sports-game-brief.md` in repo root.

## Tech Stack
- React + Vite (TypeScript template)
- Zustand for game state (single central store)
- react-router-dom for routing
- Client-side persistence only for v1 (localStorage/IndexedDB) — no backend
- 2D flat icon/sprite art for v1 (AI-generated, style-locked prompts)

## Architecture Principles
- **One shared engine, not per-sport systems.** Core engine (match sim, economy, player model, facilities, season/standings, prestige, events) is sport-agnostic. Sport-specific rules (stat weights, scoring, roster size) live in plugged-in sport modules.
- **Currency types are separated in the data model from day one** (even premium/future currency fields), so monetization can be added later without a rewrite.
- **v1 ships with exactly 2 sports.** Do not add a 3rd sport until the shared engine has been validated with 2 working end-to-end.
- Keep save/economy logic isolated in its own module — not scattered across UI components.

### Engine / sport-module split (established in step 2, validated with a second sport in the "Baseball" amendment below)
- `src/engine/types.ts` defines the sport-agnostic contract: `MatchOutcome` ('win'/'draw'/'loss'), `TickResult<TState>`, `MatchResult<TState>`, an optional `MatchContext` (`{level?, opponentLevelRange?, matchLength?}` — see "Match/economy escalation", "Continuous win-probability model", and "Baseball" below) and the `SportModule<TState>` interface (`id`, `ticksPerMatch`, `createInitialState()`, `tick(state, tickIndex, context?)`, `getOutcome(state, context?)`, `getPerformanceFactor(state, context?)`, optional `isMatchComplete?(state)` — see "Baseball" for why a variable-length match needs this). `TState` is fully opaque to the engine — sport modules own their own state shape. `context` is optional everywhere it appears — a sport module free of any win-gating concept simply never reads it.
- `src/engine/tickEngine.ts` holds three pure, timer-free helper functions (`advanceTick`, `isMatchComplete`, `finalizeMatch`) that operate generically over any `SportModule<TState>`. It must never import from `src/sports/**` or reference sport-specific vocabulary. `advanceTick`/`finalizeMatch` both take an optional `context` and thread it straight through to whichever `SportModule` methods accept it — this file never inspects or interprets it. `isMatchComplete(module, tickIndexAfterTick, state)` consults `module.isMatchComplete(state)` when the sport module defines one (a variable-length match), else falls back to the original `tickIndexAfterTick >= module.ticksPerMatch` check (a fixed-length match, e.g. soccer) — the single shared authoritative "is this match over" check, used by both the store's real completion logic and the UI's display-timing checks.
- `src/engine/economy.ts` is the single isolated home for currency math — a `REVENUE_BY_OUTCOME` table keyed only on the generic `MatchOutcome`, shared by every sport rather than redefined per sport. `calculateMatchRevenue(outcome, performanceFactor)` additionally scales revenue by the sport module's generic 0-1 `performanceFactor` (see "Match/economy escalation" below) — this file only ever consumes that single generic number, never sport-specific stats. Also holds `expectedMatchRevenue(probabilities)` (see the seventeenth amendment) — already sport-agnostic since before baseball existed.
- `src/engine/winProbability.ts` (new in the "Baseball" amendment) is the single isolated home for the level-gap-driven win/draw/loss probability model — hoisted out of `soccerModule.ts` once it became clear a second sport needed the exact same math. Sport-agnostic: takes only two numeric levels, never sport-specific state.
- `src/engine/ventureTiers.ts` (new in the "Baseball" amendment) is the single isolated home for the Adventure-Capitalist-style tier-cost/revenue/pacing formulas (`VentureTierConfig`, `VentureTierState<TState>`, `tierUpgradeCost`, `trainingEffectMultiplier`/`TRAINING_MILESTONE_LEVELS`, `tierPerTickRevenue`, `opponentLevelRangeForTier`, `autoTickIntervalMsForTier`, `tierIncomeRatePerSecond`, and — as of the "Income-rate-anchored entry costs" convention — `scaledTierConfigs`/`incomeRateAnchorMultiplier`) plus the shared `resolveVentureTierTick<TState>()` per-tick resolution helper — also hoisted out of `soccerModule.ts` for the same reason.
- `src/engine/prestige.ts` is the single isolated home for prestige/Legacy Points math (see "Prestige system" below) — sport-agnostic, takes only a scalar "total earnings," never imports from `src/sports/**`.
- `src/engine/achievements.ts` is the single isolated home for the achievement/badge framework (see "Achievements" below) — sport-agnostic, consumes only a generic `Record<string, number>` stats record, never imports from `src/sports/**`.
- A sport plugs in by implementing `SportModule<TState>` in its own folder under `src/sports/<sport>/` (see `src/sports/soccer/soccerModule.ts` and `src/sports/baseball/baseballModule.ts`) — that's the only place sport-specific vocabulary (goals/possession/shots for soccer; innings/outs/at-bats for baseball) is allowed to appear.
- The idle loop's `setInterval`s live in exactly one place — a React hook (`src/hooks/useMatchTicker.ts`). The engine, economy, and store stay fully timer-free and synchronously testable. As of the "Match/economy escalation" amendment below, the hook runs one independent interval PER auto-playing tier (real-world pacing is now a per-tier concern, via `autoTickIntervalMsForTier()`) rather than a single shared `intervalMs` parameter — see that section for why. As of "Baseball" below, this generalizes across every plugged-in sport via namespaced interval-map keys (`"soccer:tierId"`/`"baseball:tierId"`).
- ~~The Zustand store (`src/store/useGameStore.ts`) instantiates one module-scoped sport module (currently `createSoccerModule()`), reused identically by every venture tier (see below) — never forked or reconfigured per tier.~~ **Superseded** — see "Baseball" below: the store now instantiates one module-scoped instance PER plugged-in sport (`soccerModule`, `baseballModule`), each reused identically by every tier of ITS OWN sport, with a parallel tier array (`tiers`/`baseballTiers`) and parallel store actions per sport.
- `src/components/VentureCard.tsx` is fully generic over `SportModule<TState>` as of "Baseball" below — it takes a sport module instance, tier config, and tier state as props, with zero hardcoded soccer imports. Each sport gets a thin adapter component (`SoccerVentureCard.tsx`, `BaseballVentureCard.tsx`) that wires up its own store selectors/actions and passes them down — this is the actual validation of "a second sport plugs in with zero engine changes," per this build-order step's own stated purpose.

### Manual-before-automated pattern (amendment to step 2)
Classic idle games hook players with manual interaction before automation is earned. Applied to soccer, and intended as the template for every future sport:
- A single per-tier resolution path (`tickTier(tierId)` in the store) advances that tier's match by one tick — it is called identically by the idle interval and by a manual player tap, so there is never a forked "manual" vs. "automatic" simulation branch.
- Each tier has its own `managerHired` boolean (default `false`) gating its own automation: `useMatchTicker` only auto-ticks tiers where `unlocked && managerHired` are both true. Before that, a tier only advances via its own manual "Push the Attack" button.
- `managerHired` is flipped by a one-time per-tier Revenue purchase (`hireManagerForTier(tierId)`, cost from that tier's config). This cost/unlock logic lives in the store/sport-module layer, not in `src/engine/economy.ts` — it's an idle mechanic ("pay currency to unlock automation"), not part of the sport-agnostic match-outcome economy.
- Chosen design: the manual action button stays visible and usable even after automation unlocks (a supplemental boost), rather than being hidden — matches the genre convention that active play keeps some value after idle progression is unlocked.
- Future sports should follow the same shape: a manual per-tick trigger wired to the same tick-resolution path, gated automation behind a purchasable unlock, no changes to `src/engine/**`.

### Venture tiers (second amendment to step 2 — Adventure-Capitalist-style restructuring)
The single global match view was replaced with a vertical stack of independent "venture tier" cards (`Local Game → Local Tournament → Regional Championship → National League → Continental Cup → World Championship → Legends' Circuit → Galactic League → Mythic Ascension → Eternal Championship → The Multiverse Cup` for soccer — tiers 5-6 added in the eighth amendment, tiers 7-11 added in the ninth amendment, the latter hidden until a player's first prestige), each its own parallel revenue generator:
- **Reuse vs. divergence:** every tier runs its match through the exact same `createSoccerModule()` instance and the exact same `advanceTick`/`isMatchComplete`/`finalizeMatch` (`src/engine/tickEngine.ts`) and `calculateMatchRevenue` (`src/engine/economy.ts`) — none of those files changed. The only per-tier divergence is a revenue multiplier (`baseRevenueMultiplier × level`) applied in the store, in `tickTier()`, on top of `economy.ts`'s base win/draw/loss payout. `economy.ts` itself has no concept of tiers.
- Tier names/multipliers/costs are sport-specific vocabulary, so they live in `src/sports/soccer/soccerModule.ts` (`SOCCER_VENTURE_TIERS`, `tierUpgradeCost()`) — the same file that owns "goal"/"chance"/etc. A second sport (step 3) defines its own tier list the same way.
- **Store shape:** `useGameStore.ts` now holds `tiers: VentureTier[]` (id, unlocked, level, managerHired, tickIndex, match, matchesCompleted, cumulativeRevenue, lastOutcome) instead of one global match object, plus the store-level actions `tickTier`, `upgradeTier` ("Improve Training" — raises `level`, cost grows per level via a mild exponential curve), and `hireManagerForTier`.
- ~~**Unlock-threshold logic chosen:** a locked tier unlocks once the immediately preceding tier's `cumulativeRevenue`... reaches a configured threshold, auto-checked every tick.~~ **Superseded** — see "Tier unlocking as a player purchase" below; unlocking is now a deliberate spend from the current Revenue balance, not an automatic threshold.
- Revenue stays ONE global currency (`currencies.revenue`), spent/earned by every tier — `cumulativeRevenue` is a per-tier informational stat (lifetime Revenue earned from that tier), not a second currency. This preserves the currency-separation principle above.
- UI: `src/components/VentureCard.tsx` (one per tier, mapped from the static `SOCCER_VENTURE_TIERS` config in `src/routes/Home.tsx`) replaced the old single `MatchPanel`/`MatchControls`, which were deleted. No styling pass yet (that's step 9) — just structure/interactivity.

### Payout visibility fix (third amendment to step 2)
Closed the "click with no feedback until match end" gap identified in playtesting: `VentureCard.tsx` now derives a live match-progress percentage (a native `<progress>` element) from `elapsedTicks / DEFAULT_SOCCER_CONFIG.ticksPerMatch`, and a live "if the match ended now" projected-payout line. The projection reuses `getOutcome()` (now exported from `soccerModule.ts`) and `calculateMatchRevenue()` (`src/engine/economy.ts`) — the exact same functions the store calls at real match completion — so the preview can never drift out of sync with the actual payout. Purely presentational at the time it was made; superseded below by an actual economy change (Revenue is no longer only credited at completion).

### Persistence (transparent addition to step 2)
`src/store/useGameStore.ts` is now wrapped in zustand's `persist` middleware (localStorage, key `idle-sports-game-save`), per the "client-side persistence for v1" tech-stack line. `partialize` persists only `{ tiers, currencies }` — actions are always recreated fresh, never serialized. This is transparent to every tier/economy/engine call site above; none of that code changed.

### Direct-click economy model (fourth amendment to step 2 — supersedes "pay at outcome only")
Manual clicks (and equivalently automated ticks — same `tickTier()` path, no fork) now grant direct, immediate Revenue every tick. The match-completion payout is no longer the only source of Revenue; it's an additional bonus stacked on top:
- `src/sports/soccer/soccerModule.ts` adds `BASE_PER_TICK_REVENUE = 4` and `tierPerTickRevenue(config, level)` (`round(BASE_PER_TICK_REVENUE * baseRevenueMultiplier * level)`) to its additive tier-config section — the same scaling factor the completion bonus already uses, so relative tier/level progression stays consistent between the two income sources. `tick()`, `getOutcome()`, `DEFAULT_SOCCER_CONFIG`, and `createSoccerModule()` are unchanged.
- `tickTier()` in the store now adds `perTickRevenue` to both `currencies.revenue` and that tier's `cumulativeRevenue` on **every** tick, not only at completion. On the completion tick, the unchanged completion-bonus formula is added on top (`totalEarned = perTickRevenue + completionBonus`), never replacing it. (`cumulativeRevenue` still accrues every tick as a per-tier informational stat, but — as of the fifth amendment below — no longer drives unlocking.)
- **Balancing reasoning:** assumed 1 click/sec (a conservative, easily-sustained manual pace, slower than the game's own 600ms auto-tick rate). At `BASE_PER_TICK_REVENUE=4`, Local Game/level 1 earns 4 Revenue/tick, so the cheapest first purchase (Improve Training, cost 100) is reachable in `100/4 = 25` ticks ≈ 25s — the middle of the requested 20-30s window.
- **Threshold numbers chosen (originally as auto-unlock thresholds, now reused as unlock purchase costs — see below):** `local-tournament` 600→450, `regional-championship` 3000→2250, `national-league` 15000→11250 (`local-game`'s is unused). The 450→2250→11250 ladder is a clean 5x/5x growth, preserving the pre-existing design intent that unlock costs compound faster than the (unchanged, ~4x/3x/2.9x) multiplier growth per tier.
- UI: both purchase buttons show a clamped "current/cost Revenue" progress format (e.g. `Improve Training (72/100 Revenue)`, capped at the cost once affordable) instead of a flat cost, and a `+N Revenue per push` caption sits under "Push the Attack", computed via the same `tierPerTickRevenue()` helper `tickTier()` uses — never a separate hardcoded number.
- Playtested end-to-end: first Revenue is now visible after exactly one click (previously required a full 90-tick match); the first affordable purchase (Improve Training) now lands at click/second 25 (previously took multiple full matches, hundreds of clicks).

### Tier unlocking as a player purchase (fifth amendment to step 2 — supersedes automatic threshold-unlock)
Unlocking a tier is now a deliberate spend, not something that fires automatically once a stat crosses a threshold:
- `SoccerVentureTierConfig`'s `unlockThreshold` field is renamed `unlockCost` — it's paid from the player's current spendable `currencies.revenue` balance, the exact same pool `upgradeTier`/`hireManagerForTier` draw from. The three cost values are unchanged (450 / 2250 / 11250) — only the trigger mechanism changed, per this amendment's request.
- New store action `unlockTier(tierId)`: no-op if already unlocked or Revenue is insufficient; otherwise deducts `unlockCost` and flips that tier's `unlocked` to `true`. Same shape as `upgradeTier`/`hireManagerForTier` — no new pattern introduced.
- `applyTierUnlocks` (the old every-tick auto-check function) is deleted entirely — `tickTier()` no longer touches unlock state at all, only match/revenue state.
- UI: a locked tier's card now shows an always-rendered "Unlock {name} ({current}/{cost} Revenue)" button, disabled until affordable — identical pattern to the Improve Training/Hire a Manager buttons, rather than a passive progress readout.
- **This is the intended design:** because unlock cost is drawn from the same balance as every other purchase, spending on the current tier directly delays affording the next tier's unlock, and vice versa — a real, felt trade-off, not just numbers on two independent tracks. Playtested and confirmed: buying Local Game's "Improve Training" at Revenue=100 visibly reset "Unlock Local Tournament" progress from 100/450 back to 0/450 in the same instant; later, spending 450 to unlock Local Tournament at Revenue=456 instantly dropped Local Game's own Improve Training/Hire a Manager buttons from affordable back to disabled. Both directions of the tension are directly observable, not theoretical.

### Reset Progress button (seventh amendment to step 2)

- New store action `resetProgress()` in `useGameStore.ts`: sets `tiers` back to `createInitialTiers()` and `currencies` back to `{ revenue: 0 }`. Guarded by a native `window.confirm()` before calling `resetProgress()` — cheap, no new dependency, prevents an accidental misclick from wiping progress.
- Verified: reset correctly zeroes all tiers/currencies and rewrites the `localStorage` entry; canceling the confirm dialog leaves progress untouched.

### Prestige system: "Reset for Legacy" (step 7 — new architectural layer, not a tier extension)
Adventure-Capitalist-style prestige: trade this run's progress for a small, permanent currency and a handful of lasting upgrades. Deliberately built as its own layer (`src/engine/prestige.ts` + `LegacyState` in the store + `LegacyPanel.tsx`), not bolted onto the venture-tier code — tiers/economy/engine files from steps 1-2 above are unchanged by this step.
- **Trigger:** `resetForLegacy()` (`src/store/useGameStore.ts`) is a no-op unless `FIRST_PRESTIGE_TRIGGER_TIER_ID` (`'world-championship'`, exported from `soccerModule.ts`) is unlocked. The UI (`LegacyPanel.tsx`) shows a locked explainer until then, matching the venture-tier lock-card convention rather than hiding the system outright. ~~Originally checked by array position (`tiers[tiers.length - 1].unlocked`), reasoned to "stay correct if the ladder grows."~~ **That reasoning was wrong** — see the ninth amendment below, which appended 5 more tiers and broke this exact assumption; the trigger is now looked up by id specifically, not by position.
- **Legacy Points formula:** `calculateLegacyPoints(totalEarnings) = floor(sqrt(totalEarnings) / 10)` (`src/engine/prestige.ts`), where `totalEarnings` is the sum of every tier's `cumulativeRevenue` since game start or the last reset. Square-root scaling means early revenue counts for more per-point than the huge late-game numbers, so points keep climbing (not stalling) across repeated future prestiges.
  - **Constant derivation:** simulated a greedy "always spend on the most useful thing" playthrough of the real soccer ladder (unlock next tier > hire manager > buy training, in that priority, against 1.667 auto-ticks/sec once a manager's hired + 1 manual click/sec on the frontier tier) to estimate realistic total lifetime earnings at the moment a player first unlocks World Championship. Three scenarios: no managers/no upgrades (mathematical floor, ≈352k, ~59 LP), managers-but-no-upgrades (≈429k, ~65 LP), managers-and-upgrades (≈990k, ~99 LP). Picked the scaling constant `10` so this whole realistic range maps to **~59-99 Legacy Points** on a first prestige — enough to buy 1-2 of the cheaper permanent upgrades below, not the whole tree, matching the "meaningful but not trivializing" brief.
  - The live "Reset for Legacy" preview in `LegacyPanel.tsx` calls the exact same `calculateLegacyPoints()` the store's `resetForLegacy()` uses — same drift-proof preview pattern as the third amendment's match-payout projection above.
- **On confirming reset:** `resetForLegacy()` adds the computed Legacy Points to `legacy.legacyPoints`, sets `legacy.hasPrestiged = true` and increments `legacy.prestigeCount`, then rebuilds `tiers`/`currencies` via the same `createInitialTiers()`/`startingRevenue()` helpers a brand-new game uses (parameterized by the *current* permanent upgrades — see below). `legacy.legacyPoints`/`hasPrestiged`/`prestigeCount`/`permanentUpgrades` are never touched by this reset. `hasPrestiged` gates tiers 7-11's existence in the UI — see the ninth amendment below.
- **Permanent upgrade tree** (`PERMANENT_UPGRADES` in `src/engine/prestige.ts`, purchased via `purchaseLegacyUpgrade()`), kept to 4 small effects expressed generically (a revenue multiplier, a starting-capital amount, a pre-unlocked-tier count, an unlock-cost discount) so a second sport's ladder benefits with zero changes here:
  - ~~**Revenue Boost** — +10% global Revenue (per-tick and completion) per level, 5 levels, cost `20 × level` LP (20/40/60/80/100).~~ **The 5-level cap was removed** in the thirteenth amendment (Block B) — now scales indefinitely, same cost formula. Applied in `tickTier()`/`VentureCard.tsx` via `globalRevenueMultiplier()`.
  - **Head Start Capital** — one-time, 15 LP: every future run starts with 500 Revenue already banked (`startingRevenue()`).
  - **Fast Track** — one-time, 40 LP: Local Tournament starts pre-unlocked on every future run (`startingUnlockedTierCount()`).
  - ~~**Veteran Discount** — -5% to every tier's unlock cost per level, 3 levels, cost `35 × level` LP (35/70/105). Fully maxing all four costs 565 LP total — a long-term, many-prestiges goal, not a first-run one.~~ **The 3-level cap was removed** in the thirteenth amendment (Block B) — now scales indefinitely toward a 75%-off asymptote that can never be reached. Applied in `unlockTier()`/`VentureCard.tsx` via `unlockCostMultiplier()`.
  - All four are additive/no-op with zero owned (levels 0/false) so a player who never prestiges sees byte-for-byte the same behavior as before this step.
- **UI:** `src/components/LegacyPanel.tsx` + `LegacyPanel.css`, rendered above the venture-tier list in `Home.tsx`. Deliberately a different hue family (`--color-legacy*` purple/gold tokens in `index.css`, light + dark) from the tier cards' blue/green/amber, so it reads as a distinct currency/system at a glance. The reset button is guarded by a native `window.confirm()` detailing the Legacy Points about to be gained and what gets wiped — same cheap, no-new-dependency pattern as the existing Reset Progress button (seventh amendment above), appropriate given this is also a destructive-to-run-progress action.
- **Distinct from the existing "Reset Progress" debug button:** that button (`resetProgress()`) is a full wipe INCLUDING Legacy — it now also resets `legacy` back to `createInitialLegacy()`, so it stays a true "brand new player" reset rather than a confusing half-reset. `resetForLegacy()` is the only path that preserves Legacy Points/upgrades.
- **Playtested first-prestige walkthrough (the actual test of whether this works):** seeded a run with 700,000 total earnings (mid-point of the simulated range) and unlocked World Championship → preview correctly showed "83 Legacy Points" → confirmed reset → tiers/Revenue wiped to fresh-game state, `legacyPoints` became 83. Spent 20 LP on Revenue Boost lvl 1 + 15 LP on Head Start Capital (35 of 83 spent, 48 banked for next time) and separately verified Fast Track. Starting a new run afterward: Revenue began at 500 (vs. 0) and Local Tournament was already unlocked (vs. requiring a 450-Revenue grind) — both immediately felt, real head-starts — while Regional Championship onward still require the same near-full unlock grind as a first run, just ~10% faster forever from Revenue Boost and (if Veteran Discount is later bought) slightly cheaper unlocks. This is exactly the intended shape: a felt boost to the early game, not a skip of the whole run.
- Verified: build/lint clean; exercised `resetForLegacy`, all 4 `purchaseLegacyUpgrade` branches, and `resetProgress`'s full-wipe-including-Legacy behavior directly against `localStorage` state in the browser preview (native `confirm()` dialogs are auto-suppressed in the preview tool's automation, so purchase/reset actions were confirmed by patching `window.confirm` for verification purposes only — real players get the normal browser dialog). Caught and fixed one real bug during this verification: `VentureCard.tsx`'s locked-tier unlock-cost display and the unlocked-tier per-tick/projected-payout previews were reading raw `soccerModule.ts` config numbers and hadn't been updated to apply the new Legacy multipliers, so they'd have drifted from what the store actually charged/granted once any Revenue Boost or Veteran Discount was owned — fixed by routing all three through the same `globalRevenueMultiplier()`/`unlockCostMultiplier()` helpers the store uses.

### Post-prestige ladder: tiers 7-11 (ninth amendment to step 2 — mechanical extension + reveal mechanic)
Added `Legends' Circuit`, `Galactic League`, `Mythic Ascension`, `Eternal Championship`, `The Multiverse Cup` to `SOCCER_VENTURE_TIERS` (`src/sports/soccer/soccerModule.ts`), continuing the exact tier 1-6 curve — no new balance philosophy, same mechanical-continuation approach as the eighth amendment. ### Achievements: generic badge framework (eleventh amendment to step 2 — new system, not a tier/prestige extension)
A third meta-system, deliberately architected as its own layer (`src/engine/achievements.ts` + `LifetimeStats`/`AchievementsState` in the store + `AchievementsPanel.tsx`) — no changes to tiers/economy/prestige files.
- **Framework:** `AchievementConfig = {id, name, statTracked, threshold, tier, reward}`, where `statTracked` is a plain string key into a `Record<string, number>` stats record (not an enum), and `tier` is a plain string rather than a closed union — deliberately so a future achievement line or a 4th badge tier (e.g. "Platinum") never requires widening a type here, only adding data. `reward.type` IS a closed union (`'revenue' | 'legacyPoints'`, only two reward kinds exist by design), but every place that branches on it (`useGameStore.ts`'s reward loop, `AchievementsPanel.tsx`'s `rewardLabel`) uses an exhaustive `switch` ending in `assertNeverRewardType()` — so adding a third reward kind without updating both is a compile error, not a silently-wrong-currency-granted bug. `checkNewlyEarnedAchievements(stats, earnedIds)` is pure: it returns which not-yet-earned `ACHIEVEMENTS` now qualify, applies no rewards, mutates nothing — the store is solely responsible for granting.
- **First achievement line — total wins across every venture tier combined (not per-tier):** Bronze 50 wins → +200 Revenue; Silver 250 wins → +2000 Revenue; Gold 1000 wins → +10 Legacy Points.
  - **Threshold derivation:** simulated the same greedy always-be-spending policy used to tune Legacy Points (unlock next tier > hire manager > train), this time tracking wins, using an empirically-measured ~53% per-match win rate (simulated 200k matches against the actual tick probabilities). Under that hyper-engaged model: 50 wins ≈ 15.6 min, 250 wins ≈ 67 min, 1000 wins ≈ 260 min (~4.3 hours). A 50→250→1000 ladder is a clean 5x/4x escalation, matching the ratio style already used for tier costs elsewhere in this file. Real, less-than-maximally-optimized play takes meaningfully longer at every threshold — intentional: Bronze is "your first solid session," Silver is "you're invested," Gold is "hours of real cumulative play," not literal-minutes milestones.
  - **Reward derivation:** Bronze/Silver deliberately stay small relative to the same currency they're paid in (200/2000 Revenue vs. contemporaneous unlock costs of 450/11250+) — a nudge, not a shortcut. Gold pays in Legacy Points instead of Revenue specifically to bridge the two currency systems: 10 LP is enough to almost afford Head Start Capital (15 LP) outright, giving even a player who hasn't prestiged yet a first taste of the permanent currency.
  - **Scope decision, documented rather than left silent:** an achievement's Revenue reward lands directly in `currencies.revenue` (spendable immediately) but is NOT added to any tier's `cumulativeRevenue`, so it does not count toward that run's eventual Legacy Points at prestige (`resetForLegacy()` sums only `tiers[].cumulativeRevenue`). This is consistent with `cumulativeRevenue`'s documented per-tier semantics (an achievement is a cross-tier, lifetime accomplishment, not attributable to the one tier whose match happened to trigger it) — but it is a deliberate boundary, not an oversight: two players with identical tier progress will get identical Legacy Points on prestige even if one of them also banked a Bronze/Silver achievement along the way.
- **Lifetime, not per-run:** `lifetimeStats.totalWins` and `achievements.earnedIds` (`useGameStore.ts`) live outside `tiers`/`legacy.permanentUpgrades`, with the exact same persistence semantics as `legacy.legacyPoints`/`hasPrestiged` — never reset by `resetForLegacy()` (an achievement is a lifetime accomplishment; wiping badge progress on every prestige would be actively punishing, not motivating), only by the full `resetProgress()` dev wipe. Deliberate, not the only option available: per-tier `cumulativeRevenue`/`matchesCompleted` ARE reset every prestige despite their own "lifetime" doc comments — but a badge system specifically needs badges to stay earned.
- **Granting is atomic and runs on every tick, not just match completions:** a shared `applyEarnedAchievements()` helper is called from BOTH of `tickTier()`'s branches — the match-completion branch (where `totalWins` actually changes) AND the plain per-tick branch (where it currently doesn't). This was a deliberate fix during review: the first draft only checked achievements at completion, which happened to work for a completion-only stat like wins, but would have silently under-served the framework's own documented example of a future line ("total Revenue earned") — Revenue changes on *every* tick, not just at completion, so an achievement-check wired into only one branch would leave such a threshold unrecognized for up to `ticksPerMatch` ticks after it's actually crossed. Both branches now call the same generic check symmetrically, so a future per-tick stat is caught immediately. Each call applies every newly-earned reward (to `currencies.revenue` and/or `legacy.legacyPoints`) within the same `set()`, so the UI never renders a frame where a badge shows earned but its reward hasn't landed. Correctly handles multiple simultaneous grants (e.g. a hand-edited save jumping straight past all three thresholds in one tick earns all three at once, with all three rewards applied).
- **Extending this later — honestly scoped:** a new achievement line (total Revenue earned, matches played, prestige count, ...) is *mostly* config: new entries in `ACHIEVEMENTS`/`STAT_LABELS` in `achievements.ts`. Being precise rather than overselling it: a genuinely new tracked stat still needs its own field + increment site(s) (in `LifetimeStats` if it must survive prestige, exactly like `totalWins`) plus one line in `AchievementsPanel.tsx`'s `stats` record mapping that field to the key `statTracked` expects — that plumbing is unavoidable since the stat has to be tracked somewhere, and an adversarial review specifically flagged the earlier "just add config" framing as stronger than what the code actually delivers. `prestigeCount` is a rare exception needing *none* of that extra wiring, since it already lives in `legacy.prestigeCount` with the right lifetime persistence — a "reached N prestiges" line really would be pure config.
- **UI:** `src/components/AchievementsPanel.tsx` + `.css`, rendered in `Home.tsx` between `LegacyPanel` and the venture-tier list. A third distinct hue (cyan, `--color-achievement*` in `index.css`) from both the tier cards and Legacy's purple/gold — shifted from an initial teal after review flagged it as only ~19° of hue apart from `--color-success` (too close to read as clearly distinct); cyan sits a safer ~37° away. Individual badge chips use conventional bronze/silver/gold swatches (`--color-badge-*`); silver was likewise reworked from a near-identical match to `--color-text-muted` into a distinctly cooler, lighter steel-blue. An explicit cyan fallback (`.achievement-badge--other`) styles any future tier name outside those three, so "extensible beyond Bronze/Silver/Gold" holds visually, not just in the type system. Achievements are grouped by `statTracked`, so a second line just adds a second group with zero changes to the grouping logic.
- **Playtested honestly — does this add anything in a new player's first few minutes?** Manually clicked "Push the Attack" ~38 times to afford Local Game's first manager hire (~1-2 minutes of realistic new-player clicking), then let it auto-tick for roughly 4 more real minutes total. Result: **2 of 50 wins** — a small but genuinely-moving, non-zero progress bar, exactly in line with the ~15.6-minute Bronze estimate above (a single-tier, non-hyper-optimized player is slower than the multi-tier greedy simulation). Honest verdict: it does **not** feel empty or ignorable — all three badge tiers, their thresholds, and their concrete rewards are visible and legible from the very first render, and the Gold tier's "+10 Legacy Points" line quietly foreshadows the whole prestige system before a player has even unlocked it. But Bronze is genuinely **not** a first-few-minutes payoff for a normal (non-optimized, single-manager) player — it's closer to a first-session milestone. If a snappier "hooked in five minutes" moment is wanted later, the right fix is a *separate* achievement line with a much lower entry threshold (e.g. "first win," or "10 wins") — not lowering this line's Bronze to something below 50, which is calibrated as this line's real entry point, not the game's.
- **Verified:** build/lint clean. An adversarial code-review workflow (4 dimensions, 24 agents including verification) raised 21 findings and confirmed 11 as real; all medium/high-severity ones were fixed (the completion-only achievement check, the non-exhaustive reward-type branching, the Silver/teal color collisions) as detailed above; the low-severity ones (the cumulativeRevenue scope decision, this section itself being newly written) are addressed by documentation rather than code, per their own "plausibly intentional"/"expected, not yet done" framing. ### Prestige reveal cadence, uncapped Legacy sinks, training-gated match escalation, and milestone multipliers (thirteenth amendment to step 2)
Four related balance/pacing changes agreed on in design discussion, done together in one session because they interact (per-tier training level, in particular, is now touched by three of the four). No build-order step changed — this is entirely within step 2's existing systems (venture tiers, prestige, achievements were all already done).

**Block A — one hidden tier revealed per prestige, not all 5 at once.** Superseded the ninth amendment's "`hasPrestiged` reveals all of tiers 7-11 together":
- `revealedTierCount(prestigeCount)` (`soccerModule.ts`, replaces `TIERS_REVEALED_BEFORE_PRESTIGE`) = `TIERS_REVEALED_AT_START` (6) + `min(prestigeCount, MAX_POST_PRESTIGE_REVEALS)` (5) — tier 7 (`legends-circuit`) reveals after prestige #1, tier 8 after #2, ... tier 11 after #5, and reveals stop there (a 6th+ prestige only earns more Legacy Points, reveals nothing new). `isTierRevealed(tierIndex, prestigeCount)` takes the count directly now, not the old boolean — every call site in `useGameStore.ts` (`tickTier`/`upgradeTier`/`hireManagerForTier`/`unlockTier`) and `Home.tsx`'s render slice was updated to pass `legacy.prestigeCount`.
- No minimum time/earnings gate between prestiges, per instruction — a player rushing through resets quickly reveals tiers just as fast; that's an accepted trade-off (they're also giving up more mid-run progress each time), not something worth adding friction to prevent.
- `LegacyPanel.tsx` copy now names the *specific* next tier ("Prestiging again will permanently reveal The Legends' Gauntlet (4 more tiers to reveal after that)") instead of implying a single all-at-once unlock, both in the locked-explainer text and the reset-confirmation dialog.
- **`hasPrestiged` still exists** (gates the Legacy panel's locked-vs-reset-block UI) but no longer drives the reveal boundary — `legacy.prestigeCount` does. Both are lifetime fields, never reset by `resetForLegacy()`, only by `resetProgress()`'s full wipe.
- **Save-compatibility note, deliberate not a bug:** any save that already had `prestigeCount >= 1` under the OLD "reveal all 5" rule will, after this change, only see `revealedTierCount(prestigeCount)` tiers (e.g. a save with `prestigeCount: 1` now sees only tier 7, not all of 7-11). Any tiers 8-11 state that save already had (level/unlocked/cumulativeRevenue) is NOT deleted — it just becomes inert/hidden again until later prestiges re-reveal it — and gets wiped on the save's next prestige regardless, same as any tier's progress always has. This is the correct, intended consequence of the requested rule change (there is no way to "reveal exactly one tier per prestige" without an existing multi-prestige save's visible count changing to match), not something migration code should paper over.

**Block B — Revenue Boost and Veteran Discount scale indefinitely (`prestige.ts`).** `maxLevel` removed from both; `PERMANENT_UPGRADES.revenueBoost`/`veteranDiscount` no longer have the field, and `purchaseLegacyUpgrade()`/`LegacyPanel.tsx` no longer check or render a "MAXED" state for either (Head Start Capital/Fast Track are unchanged one-time toggles).
- **Revenue Boost:** cost formula unchanged (`20 × nextLevel` — already a valid indefinite-scaling formula, just previously artificially capped at level 5). This is an economic soft cap by design: technically infinite, practically self-limiting because cost keeps climbing every level forever while the benefit stays a flat +10%/level.
- **Veteran Discount — required a genuine mathematical asymptote, not just a soft cap, since a 100% discount would make unlocking free and break the economy:** `unlockCostMultiplier(level) = (1 - MAX) + MAX × RATE^level`, with `MAX = 0.75` (asymptote: never more than 75% off) and `RATE = 0.9` (each level closes 10% of the *remaining* gap to that asymptote, not 10% of the original cost). The discount is `MAX × (1 - RATE^level)`. This is safe by construction, not by floating-point luck: the multiplier is `floor + MAX × RATE^level` where `floor = 1 - MAX = 0.25` is added as its own fixed term, so even if `RATE^level` underflows to exactly `0.0` at extreme levels (verified via harness: happens by level ~15,000), the multiplier still evaluates to exactly `0.25`, never below it — the 100%-discount case is structurally unreachable, not merely improbable. Verified: multiplier stays `> 0.25` at level 100, `== 0.25` (the floor, not below) at levels 100,000 and 1,000,000.
- Cost formula also unchanged (`35 × nextLevel`) — the asymptote's own diminishing returns are what keeps very high levels not worth grinding for, so cost doesn't additionally need to gatekeep it.

**Block C — three related match/economy changes, all through the `SportModule<TState>` engine contract:**
1. **Per-tier auto-play timing.** Match length stays a fixed 90 ticks at every tier (unchanged) — only the REAL-WORLD milliseconds between auto-ticks now varies per tier: `autoTickIntervalMsForTier(tierIndex) = round(600 × 1.4^tierIndex)` (`soccerModule.ts`), tier 0 unchanged at 600ms (~54s/auto-match) climbing to ~17.4s at tier 10 (~26min/auto-match) — a ~29x spread. Manual "Push the Attack" clicks never go through this at all (they call `tickTier()` directly from `VentureCard.tsx`), so hand-grinding a high tier is never slowed by this. `useMatchTicker.ts` was rewritten to run one independent `setInterval` PER auto-playing tier at its own pace, rather than one shared interval — see the bug/fix note below for why that rewrite mattered.
2. **Margin-based bonus revenue via a generic "performance factor."** `SportModule<TState>` gained a required `getPerformanceFactor(state, context?): number`, returning a generic 0-1 scale (0 = most lopsided possible loss, 0.5 = neutral/any real draw, 1 = most decisive possible win) — `economy.ts`'s `calculateMatchRevenue(outcome, performanceFactor)` only ever consumes that number, never sport-specific stats. Soccer derives it from clamped goal differential (`MAX_MEANINGFUL_GOAL_DIFFERENTIAL = 5`, simulated: P(|diff|≥5) ≈ 3.2% of matches — a real but genuinely rare blowout tail). The bonus (`decisiveness = max(0, (factor-0.5)×2)`, revenue `= base × (1 + 0.6 × decisiveness)`) only ever applies ABOVE neutral and only ever adds on top of the flat base — a decisive win pays more, but no outcome is ever paid LESS than its own flat base, specifically so there's never a "lose more decisively for more Revenue" exploit. A minimum win (1-0) pays ~+12%, a blowout (5+) pays +60%.

### Continuous win-probability model + training milestone visibility (fourteenth amendment to step 2 — the win-probability half REPLACES Block C3 above, not additive)

**Continuous win-probability model — supersedes the thirteenth amendment's Block C3 entirely, not a tuning pass on it:**
- `MatchContext` (`types.ts`) drops `minWinLevel`, gains `opponentLevelRange?: {min, max}`. `opponentLevelRangeForTier(tierIndex)` (`soccerModule.ts`) replaces `minWinLevelForTier` — centered on the exact same `tierIndex + 1` anchor the old cliff used (preserving that number's existing calibration rather than re-deriving it), with a fixed ±2 spread clamped at a floor of 1: tier 0 is `[1,3]`, tier 10 (The Multiverse Cup) is `[9,13]`.
- On a match's FIRST tick only, `tick()` draws that match's opponent level uniformly from this range, computes `gap = opponentLevel - playerLevel`, and resolves the match's TRUE outcome via `P(win) = 1 / (1 + 10^(gap/S))`, `S = 4` — used as a direct, literal probability draw (`Math.random()` against the computed thresholds), not approximated by biasing per-tick scoring rates. `S=4` reproduces the requested anchor exactly (`gap=3` → 15.1% win chance). The formula is mathematically incapable of reaching exactly 0% or 100% at any finite gap (verified: still nonzero — `1e-250` — at `gap=1000`) — "never truly impossible, however small" holds by construction, no floor/ceiling clamp needed.
  - **Why not modulate per-tick scoring rates by gap instead (letting the outcome emerge from score, as the old model did)?** Tried first, and rejected after simulation: compounding even a modest per-tick bias over 90 independent ticks amplifies far past the intended per-match sensitivity (a naive "scale conversion rate by `10^(-gap/4)` every tick" made a mere 1-level gap already decide ~82% of matches, nowhere near the target curve), and no clean closed form maps a per-tick constant to a target match-level curve — every value tried fit one gap and drifted at others. Resolving the outcome directly, once, via the exact formula is both simpler and exactly correct by construction, which is what "simulate and adjust if needed" surfaced as the right call here.
- The remaining `1 - pWin` splits into draw/loss via `pDraw = 0.5 × closeness × (1 - pWin)`, `closeness = 4 × pWin × (1 - pWin)` (peaks at 1 exactly at `gap=0`, tapers to 0 at extreme mismatches in either direction) — draws are commonest in close matches and rare in blowouts, matching how real sports-analytics models layer draw probability on top of (rather than derive it by simply halving) a binary win-expectancy curve. At `gap=0`: 50% win / 25% draw / 25% loss. Simulated against the real `tick()` path (not just the formula in isolation): emergent long-run rates track the target curve within ~1.3 percentage points at every gap tested (`-6` to `+6`).
- The resolved outcome (plus the drawn `opponentLevel`) is stored ONCE in `SoccerMatchState` (`resolvedOutcome`/`opponentLevel`, both `undefined` until the first tick) and just read back out by `getOutcome()`/`getPerformanceFactor()` for the rest of the match — this is what keeps those two pure, idempotent functions of `state` alone: the live "if the match ended now" `VentureCard.tsx` preview calls them every render, and must never re-roll a different answer on repeated calls against the same state. `getOutcome()` no longer takes a `context` parameter at all (soccer's own implementation doesn't need it there — `types.ts`'s interface still declares it optionally, for a hypothetical sport module that resolves differently). `VentureCard.tsx` also now shows "Facing a Level N opponent" once `tier.match.opponentLevel` is defined.
- ~~**Score/outcome coherence — a deliberate, documented tradeoff, not an oversight:** the tick-by-tick home/away chance-then-conversion scoring (same formula as step 2, completely unchanged) is now purely decorative "flavor" for the live score ticker — it does not decide the payout anymore. On the match's FINAL tick only, the score gets minimally nudged (only if it doesn't already agree) so it matches `resolvedOutcome`'s sign by the time the match completes. For most of a match's 90 ticks, the live score and the "if the match ended now" line can occasionally look inconsistent (e.g. the line already says "LOSS" while the flavor score currently has the player narrowly ahead by chance) — accepted rather than engineered away, because (a) a completed match's final score is never actually shown next to its outcome badge anywhere in this UI regardless (the match resets to 0-0 the instant it completes, true since well before this session), and (b) a full "reveal a predetermined score's goals at plausible-looking moments across the match" system was judged not worth the added complexity for a purely cosmetic gap.~~ **Revisited, not just re-accepted** — real playtesting surfaced exactly the disconnect this bullet predicted, badly enough that it read as a bug. - **`getPerformanceFactor` consistency — this exact class of bug bit this game for real last session (see the thirteenth amendment's "Adversarial review and fixes"), so it was designed against from the start this time:** a new `resolvedDifferential()` helper forces the goal-differential's SIGN to agree with `resolvedOutcome` even mid-match, before the final-tick nudge has had a chance to actually align the flavor score — without it, a mid-match preview could show "LOSS" (from `resolvedOutcome`) while the flavor score currently has the player ahead by chance, letting a decisive-win-shaped margin bonus leak into a payout that's actually a loss/draw. `getOutcome()` and `getPerformanceFactor()` share one resolution path (`resolvedOutcomeOf()`/`resolvedDifferential()`) so they're structurally unable to drift apart, rather than relying on two independently-written functions staying in sync by convention.
- **Playtest across gap scenarios:** simulated match sequences at `gap=-6` (heavy favorite, ~97% win — long win streaks are common, occasional losses/draws still occur), `gap=0` (close matchup — a believable mixed W/D/L sequence), and `gap=+6` (heavy underdog, ~3% win — losses dominate, but a win is never literally impossible). Feels right: a freshly-unlocked tier is a genuine uphill climb without being a brick wall, and a well-trained tier stays mostly-but-not-always winning — the "however small, never zero" requirement is felt, not just mathematically true.

### Outcome-display consolidation, gradual score bias, and schema versioning (fifteenth amendment to step 2)
Three related fixes prompted by real observed play: two outcome-display bugs (one genuinely a stale tradeoff, one a previously-undiagnosed root cause) and a standing convention to stop this project's recurring pattern of ad-hoc save-migration patches.

**Root-cause investigation — TWO different bugs, not one.** Two symptoms were reported: (Case A) the score showed the player leading 1-0 at minute 51, but the "if match ended now" line said LOSS the whole match (match ultimately resolved LOSS — the line was right, the score was disconnected from it). (Case B) at minute 73, the match-status pill said LOSS while the projection line, in the SAME frame, said DRAW (match ultimately resolved DRAW — the line was right, the pill was wrong). These are NOT the same root cause:
- Case A is the thirteenth/fourteenth amendments' own documented "score is cosmetic flavor, only nudged at the final tick" tradeoff, working exactly as designed but feeling wrong in practice — a real bug in the sense that a documented tradeoff turned out to be a bad tradeoff once actually played, not a logic error.
- Case B is a genuinely different, previously-undiagnosed bug: `VentureCard.tsx`'s live pill (next to the score) was sourced from `tier.lastOutcome` — the PREVIOUS completed match's cached result, set once in `useGameStore.ts`'s `tickTier()` completion branch — while the projection line was sourced from `getOutcome(tier.match)`, the CURRENT match's already-resolved outcome. These are two different values about two different matches, both individually correct for what they represent, displayed adjacent to each other with nothing distinguishing them — reading as an inconsistency to a player watching the live score, even though neither value was actually wrong. Confirmed by tracing exactly when each updates: `lastOutcome` only changes at the PREVIOUS match's completion (inside the same `set()` that resets `match` to a fresh 0-0 state for the new one); the new match's own `resolvedOutcome` is then decided on ITS first tick and stays fixed for its whole duration. A tier that hasn't completed a match in the last 73+ ticks will show whatever `lastOutcome` happened to be from however long ago that was, right next to a projection line describing the CURRENT match — exactly Case B.

**Fix 1 — consolidate to one authoritative source per concept, not one variable.** `VentureCard.tsx` now computes `currentOutcome = getOutcome(tier.match)` ONCE and uses it for BOTH the live pill in the score row AND the projection line — the two can no longer disagree, since they're now literally the same read. `tier.lastOutcome` (the historical "how did the last completed match go" stat — still useful, still lifetime-tracked, unchanged in the store) moved to a new, clearly-labeled "Last Result" entry in the stats row (alongside Level/Matches/Lifetime), physically separated from the live score/clock/pill grouping instead of sitting inside it. Both share the same badge styling (renamed `.venture-card__outcome-badge`, was `.venture-card__last-result` — the old name only made sense for the historical one; reusing it for the live one would have been the exact naming-implies-meaning mismatch that helped cause this bug) so the visual language stays consistent while the DATA sources and locations are now unambiguous.

**Fix 2 — the score now gradually trends toward the resolved outcome, not just a late correction.** `soccerModule.ts`'s `tick()` still runs the same chance-then-conversion "flavor" scoring as before (it still doesn't decide the payout — the win-probability formula from the fourteenth amendment, `P(win) = 1/(1+10^(gap/4))`, `resolveMatchOutcome`, `opponentLevelRangeForTier`, is completely unchanged), but the rates themselves are now biased toward whichever side the ALREADY-RESOLVED outcome favors, growing linearly across the match (`progress = tickIndex/(ticksPerMatch-1)`, `strength = SCORE_BIAS_STRENGTH × progress`, `SCORE_BIAS_STRENGTH = 1.2`). For 'win'/'loss' this is a FIXED direction for the whole match (a resolved loss increasingly favors the opponent from tick 1 onward, not just near the end); for 'draw' there's no fixed side to favor, so it dynamically favors whichever side is CURRENTLY behind at the start of each tick, trending toward convergence rather than toward either team.
- **Biasing conversion rate alone wasn't enough — simulated before committing to the final approach:** with only `conversionRate` biased (leaving `chancePerTick` fixed), 25-70% of matches still needed the final-tick safety-net nudge even at strong bias values, because the underlying scoring process is too infrequent (~7 scoring chances per match per side) for a finishing-only bias to reliably overcome variance — a boosted conversion rate does nothing if the side never gets a chance to convert. Biasing BOTH `chancePerTick` AND `conversionRate` together (both clamped to `[0.02, 0.95]`) brought the nudge-needed rate down to ~1-5% for 'win'/'loss' at strength 1.2. A 'draw's exact-equality target is a harder statistical ask by nature and still needs the nudge ~36% of the time — but only ever by a single goal, a plausible-looking late equalizer, not a jarring rewrite.
- The final-tick nudge from the fourteenth amendment still exists, unchanged, as a safety net for the residual cases — Block 1's ask was "not JUST a late-tick nudge," not "no nudge at all"; removing it entirely would reopen the exact outcome-vs-score mismatch this fix targets for whatever fraction of matches the gradual bias doesn't fully resolve on its own.
- Verified live in the browser (not just simulated): pushed a fresh match to completion and watched the score actually move in the resolved direction as ticks advanced (e.g. 2-0 home by minute 69 for a resolved WIN), with the live pill and projection line agreeing throughout, exactly as designed.

**Block 3 — direct re-verification of `getPerformanceFactor` consistency under the CURRENT system (not the old minWinLevel system the original exploit fix was built against).** The thirteenth amendment's bonus-leak bug, and the fourteenth amendment's own fix for it (`resolvedOutcomeOf()`/`resolvedDifferential()` sharing one resolution path so `getOutcome()` and `getPerformanceFactor()` structurally cannot drift apart), predate BOTH this session's score-bias mechanism above. Since match resolution has now changed twice since that fix was written, it was directly re-tested rather than re-argued from the existing code's own comments: a harness imported the real, current `soccerModule.ts`/`economy.ts` and ran 1,350 full matches sweeping gaps from -10 (heavy favorite) to +10 (heavy underdog), checking `getOutcome()`/`getPerformanceFactor()` sign-consistency and the actual `calculateMatchRevenue()` payout at EVERY one of the 90 ticks of every match (121,500 individual observations total), plus 300 back-to-back matches on one tier checking for cross-match state drift/leakage. **Result: zero inconsistencies, zero overpay violations, found.** The shared-resolution-path fix from two sessions ago is robust to the mechanism underneath it changing again — it operates purely on `resolvedOutcome` vs. the score's sign, agnostic to WHY the score is what it is, which is exactly why it survived this session's score-bias change with no code changes needed to `resolvedDifferential()` itself.

**Schema versioning (new standing convention, not a one-off fix).** This project has now hit three separate save-compatibility bugs across past sessions — a persisted `tiers` array silently truncating the fresh one on load (ninth amendment), a hidden-tier-reveal exploit via hand-edited flags (also ninth amendment), and mid-match outcomes silently re-rolling under an old match schema (fourteenth amendment) — each patched ad hoc, after the fact, because no past shape change was ever versioned in the first place. Going forward:
- `useGameStore.ts` gained `CURRENT_SCHEMA_VERSION = 1` and a `schemaVersion` field on `GameState` itself (persisted, mirroring zustand's own outer `version` option so anyone inspecting a save's `state` blob directly can see its schema without knowing zustand's `{state, version}` envelope convention).
- **The standing rule:** any future change to what `partialize` persists — including a shape change nested inside something already persisted (a `VentureTier`, a `SoccerMatchState`, etc.) — MUST bump `CURRENT_SCHEMA_VERSION` by exactly 1 and add a new entry to `SCHEMA_MIGRATIONS` transforming the PREVIOUS version's shape into the new one. `migrateGameState()` applies every needed step in a loop from whatever version a save reports up to current — a save several versions behind walks through every intermediate step, never assumed to be only one version stale.
- **Not every compatibility gap needs a migration, though.** The mid-match `resolvedOutcome` gap (fourteenth amendment) deliberately did NOT get a migration step — there's no sensible backfilled value migration could write for an in-progress match's resolved outcome, so a tolerant/defensive read at the point of use (gating resolution on `tickIndex === 0`, not just "field absent") is the correct fix there, not a data transformation here. The one gap that genuinely IS a data transformation — a `tiers` array shorter than the current ladder — moved from its old home inside `merge()` into `SCHEMA_MIGRATIONS[0]`.
- **A real gotcha, caught before it shipped:** zustand's own version-mismatch check only fires when the persisted blob has a NUMERIC `version` that differs from the configured one (`typeof storedVersion === 'number' && storedVersion !== options.version`) — a blob with NO `version` field at all (every single real save this project has ever produced, since versioning never existed before this amendment) fails that `typeof` check and silently skips `migrate()` entirely, using the old shape as-is forever. A custom `createVersionBackfillingStorage()` wraps the default `createJSONStorage(() => localStorage)` to inject `version: 0` on read whenever the stored blob has no version field, so zustand's own check then correctly sees `0 !== 1` and invokes `migrateGameState`.
- **Tested against a real save shape, not just a synthetic one:** a harness built a representative pre-versioning, 6-tier save (matching what this project's own saves looked like before the ninth amendment added tiers 7-11) with real progress data — levels, in-flight match state, cumulative revenue, lifetime wins, earned achievements — fed it through the actual storage/migration/merge pipeline, and confirmed: the tiers array pads to 11 while every existing tier's progress (including a genuinely in-flight match) is preserved byte-for-byte; `schemaVersion` and the outer envelope's `version` both land on 1; the re-persisted blob carries `version: 1` so a second load doesn't re-migrate; an already-current save loads unchanged (idempotent); a brand-new save with no localStorage entry at all still starts at the current version. Also verified directly against this repo's own actual leftover browser save (not a synthetic one) — it migrated live with zero console errors, tiers padded to 11, version stamped to 1.

**Adversarial review and fixes.** A workflow-based review (5 lenses × adversarial verification, 13 agents) specifically hunting for interactions between this session's three changes above raised 4 candidate findings; all 4 survived adversarial verification (two lenses independently converged on the same root-cause bug, so this is 3 distinct real issues, all fixed):
- **High severity — Fix 2's gradual score bias silently inflated win-revenue by ~28%, contradicting its own "purely cosmetic" framing.** `getPerformanceFactor()`'s pre-existing `resolvedDifferential()` read the SAME `homeScore`/`awayScore` fields Fix 2's bias now manipulates — `resolvedDifferential()` only forces the differential's SIGN to agree with `resolvedOutcome`, never its magnitude. ### Outcome-independent expected payout, generalized prestige gating, and the Testing Conventions section (seventeenth amendment to step 2)
Three changes with deliberately different verification depth, per the new "Testing Conventions" section this session also added (see below) — this session is itself the first application of that rule, not just its documentation.

**Block 1 — the in-progress "projected payout" number could leak the resolved outcome even with the word hidden (moderate risk, full verification).** The sixteenth amendment hid the outcome WORD during an in-progress match, but the payout NUMBER shown next to it was still derived from `currentOutcome`/`currentPerformanceFactor` — this match's ALREADY-RESOLVED (just hidden) result. A sharp player could infer the real result from the number alone (e.g. it jumping to the flat loss payout the instant the match starts, staying flat all match, then confirmed by "Last Result" at completion).
- **Fix — a genuine, outcome-independent expected value, not a reworded resolved number.** `soccerModule.ts`'s `resolveMatchOutcome()` had its probability formula (`gap`/`pWin`/`closeness`/`pDraw`, unchanged) extracted into a new pure, exported `matchOutcomeProbabilities(playerLevel, opponentLevel): Record<MatchOutcome, number>` — `resolveMatchOutcome` now calls this internally instead of duplicating the math, so the real resolution path and the new preview are structurally unable to drift apart (the same "one authoritative source" fix pattern used repeatedly elsewhere in this file). `economy.ts` gained `expectedMatchRevenue(probabilities)`, summing `probability[outcome] * calculateMatchRevenue(outcome, 0.5)` across win/draw/loss — reusing the real `calculateMatchRevenue` directly (never reimplementing `REVENUE_BY_OUTCOME` or the margin-bonus formula). `VentureCard.tsx`'s in-progress display now computes `expectedPayout` from ONLY `tier.level` (live) and `tier.match.opponentLevel` (this match's own already-drawn, already-displayed-via-"Facing a Level N opponent" value) — never touching `resolvedOutcome`/`resolvedMargin`/the live score — so by construction the number cannot correlate with what the match actually rolls. Labeled "Expected payout: ~N Revenue" (not "Projected") to read honestly as an estimate. Pre-tick ("N/A — kickoff pending") and at-completion (word + real resolved payout) states are unchanged from the sixteenth amendment, per instruction.
- **Neutral-factor honesty, documented rather than glossed over:** using performance factor 0.5 for all three outcome terms is mathematically EXACT for draw and loss (this file's own decisiveness formula clamps to 0 at or below neutral, so neither ever receives a margin bonus at any factor), but a deliberate, honest LOWER BOUND for win specifically — a win's true average payout includes a real margin-bonus premium, but computing that premium's expectation would require either a second, separately-maintained statistical model of the margin distribution (rejected — exactly the "two copies of the same math drift apart" bug class this project has repeatedly been bitten by) or live random sampling at render time (rejected — would make the number flicker between renders and break the "impossible to correlate" guarantee's determinism). Falls back to the OLD resolved-outcome-based number only when `tier.match.opponentLevel` is undefined — a legacy pre-migration mid-match state that, per the fourteenth amendment, never got a `resolvedOutcome` either, so there is no hidden result to leak in that one case.
- **Verified — real scrutiny, per this session's own risk calibration:** a direct-import harness (9 checks) confirmed the probability formula against documented anchors (gap=0 → exactly 50/25/25; gap=+3 → exactly the ~15.1% anchor), confirmed the real `tick()`-driven resolution still matches those probabilities empirically (20,000 matches, within 2pp), confirmed `expectedMatchRevenue` exactly matches a manual sum using the real `calculateMatchRevenue` (not a coincidental reimplementation), and — the key proof — ran 3,000 matches at a fixed (level, opponentLevel) and recorded the expected-payout value at every tick of every match, split by that match's ACTUAL resolved outcome: **all 270,000 observations, across all three outcome categories, produced the exact same single number**, direct empirical proof of zero correlation rather than an argument from code inspection alone. A follow-up independent agent review (asked to specifically hunt for any leak path, formula drift, or fallback that could expose a hidden outcome) found no issues. Verified live in the browser: mid-match number stayed flat across an entire match regardless of what it ultimately resolved to, updated instantly when leveling up mid-match, and a fresh redraw after completion recomputed cleanly for the new match's own opponent.

**Block 2 — "Reset for Legacy" only checked one fixed tier, letting a player skip every tier in between at ANY prestige stage (low-moderate risk, targeted harness).** The gate only ever checked whether `FIRST_PRESTIGE_TRIGGER_TIER_ID` ('world-championship') was unlocked — at every prestige stage, forever. ### Baseball: second sport as a plugged-in module (step 3 — validates the engine abstraction)
The first genuinely new build-order step since step 2 shipped. Two parts: an architecture audit (required before writing any baseball code, per instruction) and then baseball itself — a deliberately small 3-tier validation slice, not the full arc.

**Part 0 — architecture audit result.** Confirmed BEFORE writing any baseball code, exactly as instructed: `matchOutcomeProbabilities`/`resolveMatchOutcome` (the win-probability formula) were embedded specifically inside `soccerModule.ts`, not sport-agnostic by location — but sport-agnostic by NATURE (the formula only ever consumes two numeric levels, nothing soccer-specific). `expectedMatchRevenue`/`calculateMatchRevenue` (`economy.ts`) were ALREADY sport-agnostic — no change needed, baseball calls them directly. The "cosmetic score biases toward the fixed outcome across the match" mechanism is genuinely soccer-specific by NATURE, not just by location — it operates on soccer's own "chance-then-conversion per tick" scoring model, which has no direct analog in baseball's at-bat resolution; per this project's own engine/sport-module split principle ("sport-specific rules live in plugged-in sport modules"), baseball needed its OWN analogous mechanism following the same architectural PATTERN (resolve the real outcome once, then bias a cosmetic per-tick flavor simulation toward it), not literally shared code.
- **Fix, done before any baseball code:** hoisted the win-probability formula into a new `src/engine/winProbability.ts` (`matchOutcomeProbabilities`, `resolveMatchOutcome`, plus new `matchOutcomeProbabilitiesWithoutDraw`/`resolveMatchOutcomeWithoutDraw` for the no-draw decision below) — `soccerModule.ts` now imports and calls these instead of defining them locally, so the actual resolution formula has exactly one copy, used by both sports.
- **Beyond the letter of the audit, applying its spirit:** while auditing, found the tier-cost/revenue formulas (`tierUpgradeCost`, `trainingEffectMultiplier`/`TRAINING_MILESTONE_LEVELS`, `tierPerTickRevenue`, `opponentLevelRangeForTier`, `autoTickIntervalMsForTier`) were ALSO soccer-housed-but-sport-agnostic-by-nature (pure functions over a generic tier config + numeric level/tierIndex, zero soccer vocabulary) — building baseball would otherwise have required copy-pasting these byte-identical, which is exactly the "second copy of the same math" bug class the audit was about, just not literally the three functions named in the request. Hoisted these too, into a new `src/engine/ventureTiers.ts`, alongside a new shared `VentureTierConfig`/`VentureTierState<TState>` type and a new `resolveVentureTierTick<TState>()` helper (composes `advanceTick`/`isMatchComplete`/`finalizeMatch` + the per-tick/completion revenue formulas into the one function every sport's `tickTier`-equivalent store action calls).

**Engine contract extension — a real, small, deliberate change, not silently papered over.** Baseball's match length is genuinely variable: a half-inning needs exactly 3 outs, which random hit/out/walk-style at-bat rolls take a variable number of ticks to reach (a quick 3-up-3-down half-inning vs. a long rally). The existing `SportModule.ticksPerMatch` (a single fixed number) cannot represent this. Investigated whether it could be worked around with a documented fixed-estimate fallback instead of a contract change — rejected: a fixed-tick "match" that keeps ticking past when the game (all innings played) is actually decided would either silently discard real game state, or require the sport module to internally freeze while still "ticking," both worse than the small contract addition:
- `SportModule<TState>` gained an OPTIONAL `isMatchComplete?(state: TState): boolean` (`engine/types.ts`). Soccer doesn't define one — completely unaffected, byte-for-byte the same `tickIndexAfterTick >= ticksPerMatch` check as before. `tickEngine.ts`'s `isMatchComplete(module, tickIndexAfterTick, state)` gained a required third `state` parameter (the one call site — now inside `ventureTiers.ts`'s `resolveVentureTierTick` — updated accordingly) and consults `module.isMatchComplete(state)` when present, falling back to the original check otherwise. Baseball's own `isMatchComplete` is a one-liner: `state.gameOver === true`, with `gameOver` set exactly once, at the tick that actually decides the game.
- Also added `MatchContext.matchLength?: number` — a generic, optional per-match length parameter (mirroring the existing `level`/`opponentLevelRange` fields' own genericity), for a sport whose match STRUCTURE (not just its win probability) varies by tier. Soccer ignores it entirely; baseball reads it once at tick 0 (`context.matchLength`, the tier's configured inning count) and stores it into its own opaque state as `totalInnings`, matching the "resolve once into state, read back out" pattern this file uses throughout.
- `ticksPerMatch` itself stays a required field even for baseball (`BASEBALL_ESTIMATED_TICKS_PER_MATCH = 52`, an ESTIMATE derived from expected at-bats per half-inning) — used only to size VentureCard's progress bar, explicitly documented as non-authoritative; `isMatchComplete` is what actually ends a baseball match.

**No-draw resolution — a real design decision, not a default.** Real baseball has no ties (extra innings until decided), but this project's shared economy/achievements/milestone systems assume a generic win/draw/loss `MatchOutcome` triad throughout. Two options considered: (a) an abstracted draw for triad-consistency with soccer (zero special-casing, but unrealistic for the one sport-specific rule explicitly flagged as real), or (b) genuine no-draw resolution reusing the SAME win/loss ratio the shared formula produces, with its draw probability mass proportionally redistributed. Chose (b): `matchOutcomeProbabilitiesWithoutDraw`/`resolveMatchOutcomeWithoutDraw` (`winProbability.ts`) collapse `matchOutcomeProbabilities`' draw mass into win/loss proportionally (the same technique real sports-betting "no draw" markets use) — no new probability model, just a post-processing step reusing the identical underlying formula, so nothing about the ACTUAL win-probability curve is duplicated or re-derived. `MatchOutcome`'s type itself is unchanged (still `'win'|'draw'|'loss'`) and the economy/achievements pipeline needs zero changes to support this — baseball simply never emits `'draw'` in practice, an allowed degenerate case of an already-generic type. Verified directly (see below): zero draws across 900 simulated games at a wide gap sweep.
- **Tied-after-regulation handling — a deliberate simplification, documented rather than glossed over:** the LIVE/cosmetic game does not actually simulate real extra innings when tied after the scheduled length — it applies a bounded 1-run "nudge" toward the already-resolved outcome, mirroring soccer's own final-tick nudge safety net (same reasoning: a bounded tick budget for the displayed game). The SEPARATE economic-margin resimulation (`drawResolvedMargin`, decoupled from the cosmetic game exactly like soccer's, for exactly the same "don't let a cosmetic bias leak into the economic margin bonus" reason — see the thirteenth/fifteenth amendments) DOES simulate genuine extra-innings-until-decided, since an isolated resimulation used only for the economic signal can afford to actually loop.
- **Walk-off rule, implemented for authenticity (a nice touch that directly helps "does baseball feel meaningfully different"):** the home team (bats bottom, matching real baseball's home-bats-second convention) skips or ends its final at-bat the instant it's already ahead at/past the scheduled inning count — both the "already ahead going into the bottom of the last inning" and "takes the lead mid-at-bat" cases are implemented.

**Tick granularity — one tick = one at-bat, not one inning, per instruction.** `BaseballMatchState` tracks `inning`/`half`('top'|'bottom')/`outs`/`homeScore`/`awayScore` plus the same `opponentLevel`/`resolvedOutcome`/`resolvedMargin`/`elapsedTicks` shape soccer's state has. Each tick resolves ONE simplified at-bat (out / scores a run / reaches base without scoring — a deliberate simplification with NO individual baserunner/bases-state tracking, judged not worth the added complexity for this validation slice; the simplification is visible only in HOW a run gets scored, never in whether shared math gets duplicated). A cosmetic score-bias mechanism (`scoreBiasFavorsHome`, `SCORE_BIAS_STRENGTH=1.2`, growing with an innings-based `progress` measure) biases the currently-batting team's out/score-given-not-out probabilities toward the already-resolved outcome — the baseball-native analog of soccer's own mechanism, using baseball's vocabulary (out probability / score-given-not-out probability) instead of soccer's (chance per tick / conversion rate), per Part 0's finding that this piece is not literally shareable.

**Tier calibration (3-tier validation slice, real age-level innings counts).** "Tee Time" (3 innings, T-ball/rec-league), "Little League Nights" (6 innings), "Varsity Diamond" (7 innings, high school) — `BASEBALL_TIER_INNINGS = [3, 6, 7]`, a parallel array indexed like `BASEBALL_VENTURE_TIERS` (inning count is baseball-specific vocabulary, not part of the shared generic `VentureTierConfig` shape). Costs positioned to feel like a deliberate SECOND commitment layered over soccer's own ladder, not a parallel easy track: `unlockCost` 3000/15000/70000 — interleaved between soccer's regional-championship(2250)↔national-league(11250), national-league↔continental-cup(56250), and continental-cup↔world-championship(281250) respectively, continuing the same ~5x-ish compounding soccer's own ladder uses. `baseRevenueMultiplier` 20/45/130 (between soccer's regional-championship=12↔national-league=35, etc.). Tee Time itself is its own locked-card purchase — unlike soccer's `local-game`, NO baseball tier starts unlocked (`createInitialBaseballTiers()` — every tier `unlocked: false`), since entering a whole second sport is meant to read as a deliberate milestone, not a freebie.

**Store/UI genericization — what's actually shared vs. what's deliberately still parallel.** `useGameStore.ts` gained a parallel `baseballTiers: BaseballVentureTier[]` array and four baseball actions (`tickBaseballTier`/`upgradeBaseballTier`/`hireManagerForBaseballTier`/`unlockBaseballTier`), structurally parallel to soccer's four. The actual ECONOMIC resolution (the part with real bug history) is fully shared via `resolveVentureTierTick` — both sports' tick actions call the exact same function; only the thin store-side plumbing (which array to update, which currency bucket, calling the shared `applyEarnedAchievements` helper) is duplicated at the code-structure level. This is a deliberate, documented tradeoff for this validation slice: forcibly unifying the store's `set()`-call orchestration into one fully generic action in the same session that also built baseball from scratch was judged a higher regression risk to soccer's own extensively-playtested, 17-amendments-deep behavior than a small amount of parallel-but-legible plumbing — matching this project's own Testing Conventions ("calibrate per change" and "a lighter-weight way to satisfy the same don't-skip-verification principle"). `VentureCard.tsx` itself IS fully generic now (takes a `SportModule<TState>`, `VentureTierConfig`, `VentureTierState<TState>`, and callback props, with zero hardcoded soccer imports) — `SoccerVentureCard.tsx`/`BaseballVentureCard.tsx` are the thin per-sport adapters, and this genericization (not the store plumbing) is the part that most directly validates "a second sport plugs in without changing the shared component," this build-order step's own stated purpose.
- **Deliberately independent of Legacy/prestige, per instruction:** baseball tiers are NOT gated by `isTierRevealed`/`prestigeCount`, NOT included in `resetForLegacy()`'s `allVisibleTiersUnlocked` gate check, and NOT reset by a successful `resetForLegacy()` (only the full `resetProgress()` dev wipe resets `baseballTiers`) — a soccer prestige resets THIS SOCCER RUN, not a separate, parallel venture. Baseball DOES share the same global `currencies.revenue` pool, the same Legacy "Revenue Boost"/"Veteran Discount" multipliers (already documented as "every tier, every run, forever," not soccer-specific), and the same `lifetimeStats.totalWins` achievement line (already documented as "across every venture tier combined") — verified directly, not just assumed.

### Income-rate-scaled achievement rewards (nineteenth amendment to step 2)

**The problem.** Every achievement's Revenue reward (see the eleventh/eighteenth amendments above) was calibrated once, early, as a FLAT number — but every other system in this project scales continuously with player progress (milestone multipliers, the margin-bonus formula, tier costs, Legacy multipliers). A flat reward doesn't, and becomes trivial relative to a player's actual earning power by the time a longer-horizon achievement is actually reached.

**How trivial, concretely (simulated, not assumed):** a direct-import Node harness re-ran the exact greedy "unlock next tier > hire manager > train" simulation this project's own `totalWins` thresholds were originally tuned against (see the eleventh amendment). Even at THAT ORIGINAL calibration point (50 wins, ~19 simulated minutes), the player's actual current income rate was already ~12,466 Revenue/**second** — `total-wins-bronze`'s flat 200 Revenue was worth a mere 0.016 seconds of that rate. A second, more conservative "single-tier-only" simulation (never expanding past the first tier) still showed ~681 Revenue/second at the same checkpoint — 200 Revenue worth 0.3 seconds. Neither the aggressive nor the conservative realistic play pattern comes anywhere close to making the old flat numbers feel like a "nudge" anymore; both had already made them background noise.

**The fix — Bronze/Silver rewards scale with the player's CURRENT aggregate income rate, computed fresh at the moment of grant.**
- `src/engine/ventureTiers.ts` gained `tierIncomeRatePerSecond(tier, tierIndex, config, legacyMultiplier, computeOutcomeProbabilities, estimatedTicksPerMatch)` — ONE tier's expected Revenue/real-world-second, blending its per-tick rate (`tierPerTickRevenue` × its real auto-tick pace) with its expected match-completion-bonus rate (reusing `expectedMatchRevenue` from `economy.ts` directly — never a second, separately-maintained payout estimate, matching this project's own repeated "don't duplicate the payout math" lesson). Returns exactly **0** for a locked OR manager-less tier — manual-only clicking isn't a passive "rate." Uses each tier's STRUCTURAL expected opponent (the mean of `opponentLevelRangeForTier`'s own range), not any specific in-flight match's already-drawn opponent level, so a reward granted elsewhere is never sensitive to which random opponent an unrelated match happens to be facing at that instant. `computeOutcomeProbabilities`/`estimatedTicksPerMatch` are parameters (mirroring `VentureCard.tsx`'s own props of the same names) — this file stays agnostic to which sport's with-draw or without-draw distribution applies.
- `src/store/useGameStore.ts` gained a private `currentAggregateIncomeRatePerSecond(tiers, baseballTiers, legacyMultiplier)`, summing `tierIncomeRatePerSecond` across every tier of BOTH sports (soccer via `matchOutcomeProbabilities`, baseball via the newly-hoisted `matchOutcomeProbabilitiesWithoutDrawTriple` — see below). This is inherently a store-level concern (the sport-agnostic engine layer has no way to iterate "every sport"), the same reasoning `LegacyPanel.tsx`'s/`FranchiseTab.tsx`'s own combined-stats totals already established.
- `applyEarnedAchievements` gained a 5th parameter, `getIncomeRatePerSecond: () => number` — a LAZY thunk, not a pre-computed value, so the (rare) cost of actually looping over every tier is paid only on a tick that grants something, never on the overwhelming majority of ticks that grant nothing. All 4 call sites (`tickTier`/`tickBaseballTier`'s completion AND non-completion branches) pass a closure over the CURRENT `set()` callback's own state snapshot `s` — satisfying "computed fresh at the moment of completion, not cached/precomputed ahead of time" by construction: there is no earlier-computed value anywhere for it to be stale relative to.
- `src/engine/winProbability.ts` gained `matchOutcomeProbabilitiesWithoutDrawTriple` — baseball's own with-draw-collapsed-to-0 probability adapter, hoisted out of `BaseballVentureCard.tsx` (which used to define it locally) since `useGameStore.ts`'s income-rate calculation needed the exact same shape for a second consumer. Pure dedup, not a behavior change.

**Reward-config shape.** `AchievementReward` (`src/engine/achievements.ts`) became a genuine discriminated union: `{type:'revenue', amount}`, `{type:'legacyPoints', amount}`, or the new `{type:'scaledRevenue', incomeRateSeconds, minAmount}`. Converted: `total-wins-bronze` (10s, floor 200), `total-wins-silver` (30s, floor 2000), `soccer-wins-bronze` (5s, floor 100), `soccer-wins-silver` (15s, floor 1000), `baseball-wins-bronze` (5s, floor 100), `baseball-wins-silver` (15s, floor 1000). Left alone, per instruction: the 1-win "Rookie" badge (earned near-instantly — no meaningful scaling divergence yet) and every Gold tier (already paid in Legacy Points, already scale-resistant by design). The per-sport lines use HALF the combined line's own `incomeRateSeconds` at each matching tier (5s/15s vs. 10s/30s) — preserving the exact same "per-sport line pays roughly half of the combined line's equivalent tier" relationship this project already established for the old flat numbers, just re-expressed in seconds instead of a now-meaningless absolute amount.

**Calibrating the seconds multiples — a real simulation, not round numbers picked blind.** Given how explosively this economy scales (see above), "solve for N such that N×rate reproduces the old flat number" is the WRONG calibration target — it produces a degenerate sub-second N, since the current economy had already outgrown the old numbers by 1000×+ at the very first checkpoint. Instead, `5s`/`15s` (per-sport) and `10s`/`30s` (combined) were chosen directly as legible time quantities, then VALIDATED by simulation against two very different realistic play patterns (the greedy multi-tier expander and the conservative single-tier grinder, both sports, both Bronze and Silver thresholds): in every case tested, the resulting reward landed at **~1-2% of the player's current banked wealth** — consistently proportioned, matching this project's own established reward philosophy ("a nudge, not a shortcut") across a wide variation in play style, rather than being tuned for one specific hypothetical pace.

**The floor (`minAmount`) is load-bearing, not decorative.** A player who reaches a threshold via pure manual clicking, with no manager EVER hired on any tier of either sport, has an aggregate income rate of exactly 0 by this design (manual ticking isn't a "rate") — `Math.max(incomeRateSeconds × 0, minAmount)` is the ONLY thing standing between that player and a literal 0-Revenue reward, which would read as broken. Set to each achievement's OLD flat amount, so no save is ever worse off than before this amendment, only potentially much better off. Simulation confirmed the floor essentially never binds during any realistic ENGAGED play pattern (managing even one tier easily clears the floor well before 50 wins) — it exists specifically for this one genuine edge case.

### Income-rate-anchored entry costs — baseball reset + re-cost (STANDING CONVENTION established this session)

**The problem (confirmed directly by the actual player).** Baseball's tier costs were fixed absolute numbers, calibrated once against a hypothetical "typical" progression pace. But Revenue is ONE pool shared with soccer (a deliberate design decision — see the "Baseball" amendment). A player with substantial soccer-derived wealth/income could trivially afford baseball's ENTIRE ladder from soccer pocket change, defeating baseball's intended "a real second commitment" feel. Fixed absolute entry costs are fundamentally the wrong shape for a shared-currency, multi-sport economy where a player's wealth when they reach sport N is unbounded.

**THE STANDING CONVENTION (applies to every future sport and the future re-costing of any existing one):** a sport's entry-point / ladder costs should be **anchored to the player's current aggregate income rate at the relevant moment, with a floor** — never fixed absolute numbers calibrated once. Concretely, in this codebase:
- The player's current aggregate income rate is computed by the ONE existing `currentAggregateIncomeRatePerSecond` (`useGameStore.ts`) → `tierIncomeRatePerSecond` (`ventureTiers.ts`) machinery — **never a second parallel calculation** (this project's repeated "don't duplicate the payout/economy math" lesson).
- `incomeRateAnchorMultiplier(incomeRatePerSecond, anchorSeconds, referenceFirstTierUnlockCost)` (`ventureTiers.ts`, sport-agnostic) derives a single multiplier such that the reference ladder's FIRST tier costs `anchorSeconds` worth of that income — **floored at 1** (the reference curve's own numbers).
- `scaledTierConfigs(referenceTiers, multiplier)` (`ventureTiers.ts`, sport-agnostic) rescales ONLY the three COST-side fields (`unlockCost`/`managerHireCost`/`upgradeBaseCost`) by that multiplier; `upgradeCostGrowth` is deliberately NOT scaled (a dimensionless per-level RATE, not an absolute amount). **`baseRevenueMultiplier` is likewise DELIBERATELY, PERMANENTLY excluded — see the "Revenue-scaling bug" amendment below for the real, shipped bug this exclusion fixes and corrects.** Scaling exactly those three cost fields relocates the ladder's absolute cost scale while preserving its cost SHAPE (tier-to-tier cost ratios) byte-for-byte — so a single scalar re-anchors a whole ladder's COSTS at once, and the sport's own established growth curve (baseball's ~4.6-4.7x, etc.) is untouched. **Revenue-generating fields must NEVER be touched by this or any future anchor/scaling mechanism** — see the explicit standing rule at the end of this section.
- The chosen multiplier is stored per-save (`baseballCostAnchorMultiplier`), established ONCE and never silently recomputed on every load (a moving cost target is worse UX than a fixed elevated one). Every consumer of the sport's real costs — store actions, income aggregation, AND the venture-card display — derives from the ONE shared `scaledBaseballTiers(multiplier)` helper (`baseballModule.ts`), so displayed cost can never drift from charged cost.

**The floor, and its reasoning (documented per instruction).** `incomeRateAnchorMultiplier` returns `max(1, income × anchorSeconds / referenceFirstTierUnlockCost)`, and also collapses any non-finite/non-positive income to `1`. The floor of `1` (= the sport's ORIGINAL, carefully-simulated reference numbers, completely unscaled) protects a genuinely fresh/near-zero-income player from the OPPOSITE failure mode: a sport becoming suspiciously CHEAPER than its own baseline just because "current income" reads as near-zero for someone who also hasn't built anything yet. So the anchor only ever makes a sport's entry MORE expensive (for a wealthy player), never cheaper than its designed baseline.

**Baseball's anchor: `BASEBALL_COST_ANCHOR_SECONDS = 60`** (`baseballModule.ts`) — Tee Time (reference unlockCost 3000) costs one full minute of the player's current combined income to unlock. Chosen deliberately: entering a whole second sport should read as a real commitment (~a minute of income, not a fraction of a second), but not a wall — and baseball's own ~4.6x per-tier growth then compounds that entry anchor into a genuinely steep late-game ladder on its own. Lives in baseball's module because "how big a commitment is entering THIS sport" is a per-sport design decision; a future third sport picks its own anchor-seconds the same way.

**The DELIBERATE, INTENTIONAL reset (per explicit player request — NOT a bug, documented so it's never mistaken for a regression later).** The v5→v6 migration (`SCHEMA_MIGRATIONS[5]`) does five things, in order:
1. Snapshots the save's income rate that SURVIVES the reset — soccer only, since baseball's own income is being zeroed in the same step — via the shared machinery above (passing an empty baseball array to the same `currentAggregateIncomeRatePerSecond`, so it's a reuse, not a parallel calc). **Why soccer-only, not both-sports:** an adversarial-review lens flagged that counting baseball's current income — which the reset is about to DESTROY — would inflate the anchor and could WALL a baseball-heavy save's re-entry (Tee Time priced against a transient peak the player no longer has post-reset, instead of the income they'll actually fund the re-climb with). Anchoring to the persisting (soccer) income prices baseball's re-climb against the player's real go-forward economy. For the actual target player (soccer-rich, baseball lightly touched) the two bases are nearly identical anyway; the difference only matters — and only helps — for a baseball-heavy save. This is a deliberate refinement of "aggregate income" → "aggregate income that survives the reset."
2. Derives + stores `baseballCostAnchorMultiplier` from that snapshot (wrapped in a try/catch so a corrupted-element save can never throw-and-discard the whole migration — falls back to the floor).
3. Resets `baseballTiers` entirely to `createInitialBaseballTiers()` — every tier locked, level 1, zero matches/cumulativeRevenue, no manager: exactly a brand-new player's baseball state.
4. Resets `lifetimeStats.baseballWins` to 0 (so the "Baseball Wins" achievement line is re-earned under the corrected economy). `totalWins`/`soccerWins` are NOT touched.
5. Removes the baseball-specific achievement ids (derived from `ACHIEVEMENTS` by `statTracked === 'baseballWins'`, not hardcoded) from `achievements.earnedIds`. All other earned badges (the combined `totalWins` line, the `soccerWins` line) are kept.

**Explicitly NOT touched by the migration:** soccer's `tiers` (byte-for-byte preserved), the shared `currencies.revenue` balance itself, `legacy`/prestige state, and the combined `totalWins` line's badges/progress (and `soccerWins`). `resetForLegacy()` also deliberately never touches `baseballCostAnchorMultiplier` or baseball tiers (matching how it already leaves baseball independent); `resetProgress()`'s full dev-wipe resets the multiplier back to `1` along with everything else.

### Revenue-scaling bug in the income-rate anchor — cost-anchoring must NEVER touch revenue fields (follow-up session, corrects the amendment above)

**Player-reported bug (confirmed via screenshots, real save).** A Level-1, never-upgraded, 2-match Tee Time (baseball) was showing **+589,458 Revenue per at-bat** and **~10,561,122 expected payout** — while a Level-13, heavily-trained, 139-match The Sunday League (soccer) showed only **+312 per push** and **~7,788 expected payout**. A never-invested-in tier out-earning a heavily-invested one by ~1,900x completely defeated the anchor fix's purpose: if baseball's INCOME scales up by the same wealth-anchor multiplier as its COSTS, the real grind ratio (clicks/matches needed per purchase) hasn't changed at all — it just looks bigger. The player would still get an unearned advantage, just with less-obvious numbers.

**Diagnosis.** `scaledTierConfigs()` (`ventureTiers.ts`) was multiplying FOUR fields by the anchor — the three legitimate cost fields (`unlockCost`/`managerHireCost`/`upgradeBaseCost`) **and** `baseRevenueMultiplier`, a REVENUE-generating field, not a cost. The original instruction that introduced this system only ever specified cost-side fields ("Recompute baseball's entire 6-tier cost ladder (unlockCost/managerHireCost/upgradeBaseCost/etc.)") — the amendment above's own author (a prior session) generalized the "etc." to include `baseRevenueMultiplier` and then talked itself into a plausible-sounding but backwards justification for it (see the struck-through bullet above: "NECESSARY for correctness... otherwise unplayably slow"). Every revenue-generating call site (`tierPerTickRevenue`, `tierIncomeRatePerSecond`, `resolveVentureTierTick`'s completion-bonus math, `VentureCard.tsx`'s displayed expected-payout) is a correct, generic function that simply reads whatever `config.baseRevenueMultiplier` it's handed — none of them were themselves buggy; they were all just fed a poisoned config by the one function that scaled a field it should never have touched. Confirmed by grep: `scaledTierConfigs()` was the ONLY place in the whole codebase that scaled `baseRevenueMultiplier`.

**Fix.** `scaledTierConfigs()` now scales ONLY the three cost fields; `baseRevenueMultiplier` passes through completely untouched, at every multiplier, for every tier. Every downstream consumer picks this up automatically (they all derive their config from `scaledBaseballTiers()`/`scaledTierConfigs()`, never a second copy), so this is a single-point, single-line fix (removing one line from the returned object).

**Migration vs. code-only fix — investigated, not assumed: this is a PURE CODE FIX, no new schema migration.** The STORED `baseballCostAnchorMultiplier` value is derived by `incomeRateAnchorMultiplier(incomeRate, anchorSeconds, BASEBALL_VENTURE_TIERS[0].unlockCost)` — its formula has no `baseRevenueMultiplier` term anywhere, and the income-rate snapshot it's derived from (`SCHEMA_MIGRATIONS[5]`) passes an EMPTY array for baseball tiers (see the soccer-only-anchor fix above), so the code path that reads `config.baseRevenueMultiplier` never even executes during that migration. Confirmed independently by this session's adversarial review (migration-necessity lens): a save that migrated v5→v6 under the OLD buggy `scaledTierConfigs` has a byte-identical `baseballCostAnchorMultiplier` to one migrated under the fixed code — the stored number was never touched by this bug in either its buggy or fixed form. No `CURRENT_SCHEMA_VERSION` bump; every existing save is corrected automatically the instant this code ships, with zero migration needed.

### Prestige now resets BOTH sports — franchise-wide Legacy Points + anchor recomputation (corrects a real prestige-defeating bug)

**The problem (player-confirmed).** "Reset for Legacy" reset only soccer's `tiers` and the shared `currencies.revenue`. Baseball's tier levels, unlocked status, and manager-hired status all survived a prestige completely untouched. Because Revenue is ONE shared pool, a developed baseball economy refilled the wallet almost immediately after every reset — so prestige stopped being the genuine "restart your run, offset by small permanent bonuses" trade it exists to be, and became a mild inconvenience a baseball-invested player could shrug off. This was never a deliberate design decision; it was the accidental result of baseball being added as an intentionally-independent second sport long after `resetForLegacy()` was written against soccer alone.

**Part 1 — `resetForLegacy()` now resets baseball too** (`useGameStore.ts`). It sets `baseballTiers: createInitialBaseballTiers()` — the exact same helper a brand-new save uses, so neither sport can drift from "what a fresh player has":
- **All 11 tiers back to LOCKED, including Tee Time.** Baseball deliberately has no free starting tier the way soccer's Sunday League does (see the "Baseball" amendment), so a true reset is *fully* locked, not "first tier free."
- `level` → 1, `managerHired` → false, `matchesCompleted`/`cumulativeRevenue` → 0, `lastOutcome` → null, `tickIndex` → 0, and the in-progress `match` object replaced with a fresh `baseballModule.createInitialState()` (so a mid-inning game in flight at reset time is genuinely cleared, not carried over).
- Soccer's own reset is byte-for-byte unchanged (still `createInitialTiers(permanentUpgrades)`, so the Fast Track permanent upgrade still pre-unlocks its tiers), and `currencies.revenue` still resets to `startingRevenue(...)` exactly as before — that half was already correct.

**Part 2 — the wealth anchor is RECOMPUTED at reset time, against the POST-reset economy.** Leaving the old pre-reset `baseballCostAnchorMultiplier` in place would price freshly-*relocked* baseball tiers for wealth the player just gave up — Tee Time still costing millions on what is otherwise a fresh start, a confusing broken-feeling mismatch. The migration's inline anchor logic was **extracted into a shared `computeBaseballCostAnchorMultiplier(soccerTiers, baseballTiers, permanentUpgrades)` helper**, now the ONE authoritative implementation used by both places that ever establish this value (`SCHEMA_MIGRATIONS[5]` and `resetForLegacy()`) — reused, per instruction, never reimplemented alongside. Both callers pass whichever economy is the correct basis (the migration passes soccer-only since it's destroying baseball's income; the reset passes the post-reset arrays for *both* sports since it destroys both), and the helper just measures what it's handed. In practice the post-reset arrays have no managers anywhere, so `tierIncomeRatePerSecond` reports 0 for every tier and the multiplier floors to **1** — baseball's own unscaled reference numbers, the correct pricing for a player starting over. It's computed from the real arrays rather than hardcoded to `1` so it stays correct by construction if a future permanent upgrade ever grants post-reset income.

**Part 3 — Legacy Points now reward the WHOLE franchise's earnings.** New shared `totalFranchiseEarnings(soccerTiers, baseballTiers)` sums both sports' `cumulativeRevenue` and is the single input to `calculateLegacyPoints`. **The sqrt-based formula itself is completely unchanged** — only what feeds into it. Baseball is included precisely because this same reset now sacrifices baseball's progress too; rewarding only soccer's earnings for a two-sport sacrifice would be strictly worse than before. `LegacyPanel.tsx`'s live preview calls the *same* shared helper as the store, so the previewed number can never drift from the number actually granted (this project's standing drift-proof-preview pattern). Achievement-granted Revenue is still excluded, since it never enters any tier's `cumulativeRevenue` — matching that field's own long-standing documented scope.

**Explicitly UNCHANGED (verified, not assumed):**
- **Baseball is still never prestige-gated, in either direction.** The gate remains soccer-only (`allVisibleTiersUnlocked` over `tiers`): baseball is not a prerequisite for prestiging, and prestige never gates baseball's unlocks. This change is about *what a reset wipes*, not about adding gating.
- **All three achievement lines survive untouched** — `lifetimeStats` (totalWins/soccerWins/**baseballWins**) and every earned badge id including `baseball-wins-*`. Note the v5→v6 *migration* deliberately DOES clear `baseballWins` + baseball badges; `resetForLegacy()` deliberately does NOT inherit that, because achievements are lifetime accomplishments per this project's existing convention.
- **Legacy Points balance and all 4 permanent upgrades persist**, as always.

**Migration vs. pure code change — investigated, not assumed: PURE CODE CHANGE, no migration.** `CURRENT_SCHEMA_VERSION` stays **6**, `partialize`'s field list is unchanged (same 8 fields), and no nested persisted shape changed (`VentureTier`, `BaseballVentureTier`, `LegacyState`, `LifetimeStats`, `AchievementsState` all identical). Only the *behavior* of an action and the *input* to a derived calculation changed. Existing v6 saves therefore load byte-identically and — correctly — **keep their baseball progress and elevated anchor until the player actually chooses to prestige**; retroactively wiping baseball on load would destroy progress the player never opted to trade away. (The extraction of the migration's anchor logic into the shared helper was separately proven behavior-preserving: a v5 save still migrates to the byte-identical multiplier `864.0786341025041` it produced before the refactor.)

**A KNOWN, ACCEPTED one-time "baseball catch-up" on the first post-change prestige (documented, deliberately NOT migrated away).** Surfaced by four of this session's five review lenses independently, so it is recorded here rather than left silent. Baseball's `cumulativeRevenue` was previously zeroed only by the v5→v6 migration and `resetProgress()` — never by a prestige. So on a save that has prestiged at least once *since* that migration, baseball's ledger spans several soccer runs, and the FIRST prestige after this change credits all of it toward Legacy Points at once. This is accepted as correct-enough, for reasons that survived adversarial scrutiny:
- **It is not a double-count.** Baseball's earnings were never an input to *any* previous Legacy Points grant (the input was soccer-only), and baseball tiers were never sacrificed by any previous prestige. This reset is the first time that ledger is destroyed, so crediting it exactly once, at the moment it is first given up, is coherent — not payment for something already cashed out.
- **The sqrt curve makes the transition under-pay, not over-pay.** Because `calculateLegacyPoints` is concave, one lumped grant over N runs' earnings is *less* than N separate grants would have been. Measured lifetime Legacy Points on the shipped path came out at 0.63–1.00× the new design's own steady state — the alarming-sounding multiples only appear when compared against the soccer-only baseline this change deliberately replaced.
- **A migration would have been net-harmful.** Zeroing `baseballTiers[].cumulativeRevenue` on load would strip genuinely-current-run earnings from the larger population that has NOT prestiged since v6 (for them the ledger is entirely legitimate this-run revenue), and would also blank the per-tier "Lifetime" stat each baseball card displays. Under-crediting real players to tidy a transitional edge for a few was judged clearly worse.
- **The schema convention does not fire here** — it is explicitly scoped to `partialize`'s field list and nested persisted *shapes*, and this file's own "not every compatibility gap needs a migration" carve-out covers exactly this case: nothing's shape changed, only which action resets a field.
- The copy was corrected rather than the data: `totalFranchiseEarnings`' doc comment and the Legacy panel's preview no longer claim "this run" (they say the earnings *being given up by this reset*), since that phrasing was the only genuinely wrong part. It self-corrects permanently after the first post-change prestige, when both ledgers fall in step.

### Objectives — a rotating set of short-term goals on the Hub (new system)

A third progression system alongside achievements and Legacy: **2-3 short-term objectives, always active, shown directly on the Hub** (not a fourth building, not inside Franchise HQ — the Hub is the screen a player lands on every load, and the whole point is a low-friction glance). New engine module `src/engine/objectives.ts` + `ObjectivesPanel.tsx`; the tier/achievement/prestige systems are otherwise untouched.

**Relationship to achievements — deliberately a separate system, not more achievement lines.** Achievements are permanent, one-time, lifetime milestones at fixed absolute thresholds. Objectives are repeatable, short-horizon, and measured as a **delta from when they were assigned**, so the same objective can be drawn again later and still mean something. They share the reward *math* and nothing else.

**Config-driven pool (`OBJECTIVE_POOL`), same extensibility pattern as `AchievementConfig`.** Each entry is `{id, statTracked, targetKind, targetAmount, describe(resolvedTarget), rewardIncomeRateSeconds, rewardMinAmount, requiresStatPositive?}`. Adding an objective type is a config addition; adding a genuinely new tracked stat additionally needs one `OBJECTIVE_STAT_LABELS` entry, one `OBJECTIVE_STAT_SCOPES` entry, and the store supplying that key — the same honest "mostly config" scope the achievements section documents. `OBJECTIVE_STAT_LABELS` is `as const` with `ObjectiveStatKey` derived from it (the same typo-catching pattern `STAT_LABELS`/`StatKey` use).

**ONE shared pool spanning both sports**, not per-sport queues, so a player is nudged across their whole franchise rather than handed parallel to-do lists.

**Baseline-delta progress.** On assignment an objective captures `baseline` (the stat's value right then) and a resolved `target`; `progress = current − baseline`, clamped at 0. This avoids any "session" concept entirely, which suits this always-persistent, no-login architecture. `target` is stored rather than re-read from config so an income-scaled objective can't move its own goalposts mid-flight, and an in-flight objective survives a future pool rebalance unchanged.
- **`ObjectiveStatScope` (`lifetime` vs `run`)** exists because a prestige zeroes tier state. A run-scoped objective assigned before a prestige would otherwise be left with a baseline *above* the post-reset value — permanently unreachable. `resetForLegacy()` re-baselines exactly the run-scoped ones (`rebaselineRunScopedObjectives`) and deliberately leaves lifetime ones (the win counters, which survive a prestige by design) alone.
- **Income-scaled targets (`targetKind: 'incomeRateSeconds'`)** are required for the Revenue objective specifically: this economy spans many orders of magnitude, so any fixed Revenue number would be an impossible wall early and instant noise later. "About 90 seconds of your current income" stays meaningful at every stage.

**The pool (8 entries), with reasoning.** Two cross-sport win objectives at different sizes (a quick one and a stretch one, so the active set can mix horizons); one per-sport win objective each (nudging toward a neglected sport); two training objectives (rewarding the *spend* loop rather than the passive-idle loop); one unlock objective ("push your frontier"); one income-scaled Revenue objective.

**Reward calibration — simulated, not round numbers.** Rewards are Revenue-only and computed by the **existing** rate-based machinery: `scaledRevenueReward` was **extracted** from the store's inline achievement-granting code into `engine/economy.ts` and is now called by *both* systems, so a second drifting copy is structurally impossible (this project's repeated duplicated-economy-math bug class). Calibration: simulated each objective's completion time across four game states (early / early-mid / mid / late), took the median, and set `rewardIncomeRateSeconds ≈ 0.08 × median_time`, giving **~24% aggregate income uplift** with 3 concurrent objectives — meaningful but not dominant. Two findings came directly out of that simulation:
- Reward is now **monotonic in effort** (a longer objective never pays less), which the first pass was not — `unlock-1` was paying 4.3× its effort ratio while `training-20` paid 0.07×.
- **`training-20` was cut to `training-10`**: 20 training levels costs ~28 minutes at the median (training cost grows exponentially), far outside the 29–246s band every other entry occupies and not a "short-term" goal at all.

| objective | median time | rewardIncomeRateSeconds | floor |
|---|---|---|---|
| `unlock-1` | 6s | 3 | 45 |
| `training-5` | 33s | 3 | 45 |
| `wins-any-5` | 51s | 4 | 60 |
| `earn-revenue-90s` | 90s | 7 | 105 |
| `wins-baseball-10` | 100s | 8 | 120 |
| `training-10` | 147s | 12 | 180 |
| `wins-any-20` | 206s | 16 | 240 |
| `wins-soccer-10` | 246s | 20 | 300 |

`rewardMinAmount` (= `15 × rewardIncomeRateSeconds`) is the floor for a genuinely zero-income player — one who has never hired a manager anywhere, for whom `tierIncomeRatePerSecond` returns exactly 0 by design. **`OBJECTIVE_FLOOR_INCOME_RATE = 15`** floors the *rate* an income-scaled TARGET is sized against, at the same 15/sec that `rewardMinAmount` already implicitly assumes — so the reward-to-target ratio holds by construction at zero income instead of diverging (see the review fixes below).

**`requiresStatPositive` — an eligibility gate the simulation forced.** A shared cross-sport pool can otherwise hand a player an objective they structurally cannot progress: "win 10 more baseball matches" for someone who has never unlocked a baseball tier could *never* complete, occupying one of only three slots indefinitely (the simulation showed baseball wins genuinely unreachable in the early-game state). `wins-baseball-10` is gated on `baseballTiersUnlocked > 0`. Checked at draw time only, so a prestige never yanks an in-flight goal away.

**Rotation.** `drawObjective` excludes any pool entry whose `statTracked` is already in play (rather than merely the same id — otherwise "win 5" and "win 20" could show simultaneously and read as one duplicated goal), **plus** the just-completed ids on a refill, so a finished objective can't reappear in the same frame it completed in. Deliberately simple, no weighting or anti-repeat history.

**Hub display reads the same shared state as everything else** — no stat is recomputed a second way. `selectObjectiveStats` (exported by the store) is the ONE place the record is assembled, and the store's own grant path uses that identical function; it reuses `lifetimeStats`, `totalFranchiseEarnings`, and `visibleTierUnlockProgress`/`revealedTierCount` rather than deriving anything fresh. The panel renders progress with `objectiveProgress`, the exact pure function the store judges completion with, so what a player sees at 100% is precisely what pays out. The panel selects the underlying store fields individually and assembles locally, because returning the fresh record straight from a zustand selector would re-render every tick.

**Evaluated from EIGHT call sites** via one shared `resolveObjectivesForState`: the four tick branches (soccer/baseball × completion/non-completion) AND the four purchase actions (`upgradeTier`/`unlockTier`/`upgradeBaseballTier`/`unlockBaseballTier`). Both halves are required, because objectives track stats that move on every tick (`franchiseEarnings`) *and* stats that move **only** on purchases (`totalTierLevels`/`tiersUnlocked` — 3 of the 8 pool entries). `hireManagerForTier`/`hireManagerForBaseballTier` are deliberately excluded: they move no tracked stat. The common no-op tick bails before touching the income rate, which loops every tier of both sports.

**Schema migration — confirmed required, not assumed.** `objectives` is a genuinely new `partialize` field, exactly the case the versioning convention exists for. `CURRENT_SCHEMA_VERSION` **6 → 7**; `SCHEMA_MIGRATIONS[6]` assigns an existing save a full valid set **baselined against that save's current stats**, not zero — a veteran save with hundreds of wins and dozens of tier levels would otherwise get 2-3 instantly-complete objectives that pay out on the next tick for work done before the system existed. Both tier arrays are length-guarded and the whole derivation is try/caught (an uncaught throw in a migration step is swallowed by zustand's persist hydrate and discards the *entire* migration). `merge()` sanitizes `objectives` on every load for the already-at-current-version corrupted case; the top-up back to a full set self-heals on the next tick.

### Daily and Weekly objective tiers — the first date/clock logic in the project

Two new objective TIERS layered on the rotating Objectives system above, rendered as new sections inside the **same Hub Objectives card** (not a separate area, not a fourth building). Exactly one Daily and one Weekly is active at a time. A third "Season" tier was explicitly deferred and is not scaffolded anywhere.

**Everything shared is genuinely shared, not re-implemented.** Both tiers reuse the existing `ObjectiveConfig` shape, the `ActiveObjective` baseline-delta mechanism, the progress math (a new private `progressForConfig` that `objectiveProgress` itself now delegates to, so all three tiers score identically), the draw/eligibility rules (`requiresStatPositive`), the run-vs-lifetime scope distinction, and — per instruction — `economy.ts`'s shared `scaledRevenueReward` for every Revenue payout. `objectives.ts` gained exactly one import (`economy.ts`, itself sport-agnostic and this project's documented home for currency math) so the reward function can't be passed in as a swappable parameter and quietly diverge.

**What differs is only three things**, and each is a deliberate consequence of the spec:
1. **One slot per tier**, with a reset BOUNDARY instead of rotate-on-completion.
2. **Targets scaled for a period of play** (see calibration below).
3. **Capped completion** — pays out once, then holds a "✓ Completed — back in <time>" state and does NOT redraw until its own boundary passes.

**Reset semantics.**
- **Daily** compares today's LOCAL calendar date key (`localDateKey`, `'YYYY-MM-DD'` from local `getFullYear/getMonth/getDate`) against a stored `lastResetDate`. Any difference is a new day. Comparing date keys rather than elapsed milliseconds is what puts the boundary at the player's own midnight, and it is inherently DST-proof — a 23- or 25-hour day is still exactly one date change, never two and never zero.
- **Weekly** uses a ROLLING 7 days from a stored `lastResetMs`, deliberately not calendar-week aligned: a weekday choice would need a timezone policy and would hand a player who first plays on a Saturday a one-hour "week".
- `PeriodicObjectiveState` stores **both** fields on every reset and each kind reads only the one that defines its own boundary. That keeps ONE state shape and ONE reset path for the two kinds while leaving each rule expressed in the units it is actually about. `msUntilPeriodReset` powers the countdown from those same fields (daily via `setHours(24,0,0,0)`, the DST-correct "start of next local day").
- **`completed` is a stored flag, not re-derived from progress** — a genuine requirement, not redundancy. A rotating objective is replaced the instant it completes so it can't pay twice; a capped one stays in place, so without the flag it would re-qualify and pay out on every subsequent tick. It also survives a prestige re-baseline (which can push a run-scoped stat back below its baseline) without the reward becoming re-claimable.
- **Grant, THEN reset**, in that order, within one evaluation: a completion landing in the same instant the boundary passes is paid before the slot rolls over. The reverse order would silently swallow a legitimately earned reward at midnight.
- **No catch-up, by construction.** A reset always anchors both boundary fields to *now*, so returning after 5 missed days or 3 missed weeks yields exactly ONE fresh objective and a full fresh period from the moment of return. Missed periods are not a thing that can be owed.
- **Clock-rewind guard:** if `now` is before the stored reset time (manual change, NTP/timezone correction), the weekly window re-anchors to now rather than pointing into the future — so a player isn't stranded waiting out the old timestamp *plus* 7 days. It never grants and never redraws, and cannot shorten a window: the next weekly is still a full 7 days from that re-anchored moment.

**Evaluated from NINE call sites, not one.** The eight existing `resolveObjectivesForState` sites (soccer/baseball × tick-completion/non-completion, plus `upgradeTier`/`unlockTier`/`upgradeBaseballTier`/`unlockBaseballTier`) now resolve both periodic slots too, sharing ONE stats snapshot and ONE memoised income-rate snapshot with the rotating set — so simultaneous rewards across all three tiers are priced off the same instant of the economy. This follows the previous session's own hard-won lesson (objectives were briefly evaluated only on ticks, leaving purchase-driven ones frozen), applied up front rather than after the fact. The ninth site is a new `refreshPeriodicObjectives()` store action driven by a new `usePeriodicObjectives()` hook (30s interval, mounted in `App.tsx` alongside `useMatchTicker`): a boundary can pass with nothing else happening at all — a player with no manager hired anywhere produces no ticks and no purchases, so nothing would notice midnight. It reads via `get()`, **bails before `set()` whenever nothing changed**, and so costs no re-render and no localStorage write on the (essentially always) no-op wake-up. It lives in `useMatchTicker.ts` to honour this project's "setIntervals live in exactly one module" convention, as a separate hook because it watches the clock, not the tiers.

**Target calibration — simulated against the real engine, four game states.** The load-bearing fact: **this game has no offline-progress system** (`useMatchTicker`'s intervals only run while the app is open), so "a full day's play" means the time a player actually spends IN the app that day, not 24 hours of idle accrual. Candidate targets were measured across early / early-mid / mid / late states under the same hyper-engaged assumption every prior calibration in this file used (a sustained 1 manual click/sec on the frontier tier plus every managed tier's real auto-tick pace). | Daily | soccer wins | 60 | 17.5 min | 85 |

Daily lands in a tight ~10-18 min cluster (roughly 10-20× a rotating objective's 29-246 seconds — the "a day's goal, not a two-minute errand" step-up this tier exists for); weekly in an unusually tight 83-92 min band, which matters more there because **every weekly pays the same Legacy Points**, so they should cost roughly the same effort whichever is drawn. Rewards continue the rotating pool's own conventions exactly: ≈0.08 × median completion time, monotonic in effort, floors at `15 × rewardIncomeRateSeconds`, and strictly increasing across tiers (rotating max 20 < daily min 50; daily max 85 < weekly min 400).

Two calibration decisions worth recording:
- **No training objective in the WEEKLY pool**, unlike daily. Upgrade cost is exponential in level, so a training target's completion time explodes with player state: 40 training levels measured 12 min (mid), 172 min (late) and **69 hours** (early) — a ~200× spread, versus ~10× for win targets and under 2× for the income-scaled Revenue one. A single weekly slot holding the only Legacy-Point-bearing objective in the game is the worst possible place for that variance. Daily keeps its own training entry at a much smaller target (20), where the spread is tolerable and a missed day costs nothing.
- **No `tiersUnlocked` objective in either pool**, unlike the rotating one. That stat has a hard ceiling (every tier unlocked), so a single-slot objective on it could be literally unachievable for a whole day or week. The rotating tier can carry `unlock-1` safely because it sits beside two workable siblings and rotates out on any completion.
- The COUNT-based state spread is documented rather than engineered away: a brand-new player's early state is several times slower for any fixed count (100 wins ≈ 92 min there). Dailies are a bonus layer, missing one costs nothing a player had, and the income-scaled Revenue entry — whose completion time is nearly state-independent by construction (10-16 min across all four states) — is always in the draw as the equaliser.

**Weekly Legacy Points: a flat 5, and why that number.** Deliberately NOT `calculateLegacyPoints`' sqrt-earnings formula, per instruction — that formula converts a run's *sacrificed earnings* into points, and a weekly objective sacrifices nothing; reusing it would also make the reward scale with the player's economy, which is exactly the wrong direction, since LP scarcity is what keeps prestige meaningful. Measured against what prestige actually pays, using the real `calculateLegacyPoints`: 300k earnings → 54 LP, 700k → 83, 2M → 141, 47M → 685 (that last is a real measured save). A greedy simulated run reaches prestige eligibility in ~10.5 minutes of app-open play, so an engaged player banks hundreds to a couple of thousand LP a week from prestige alone. Against that, 5 LP/week is:
- ~6% of a single EARLY prestige, ~3.5% of a mid one, under 1% of a developed one — modest at every stage, and automatically *more* modest the further a player gets;
- ~0.25% of an engaged player's weekly prestige income;
- never a path: at 5/week it takes 4 weeks of perfect weeklies to afford Revenue Boost level 1 (20 LP), and a full simulated year of relentless completion yields 265 LP — about three early prestiges' worth spread over twelve months.

It is still real at the scale that matters most: a player who prestiges rarely reaches Head Start Capital (15 LP, the cheapest permanent upgrade) after three weeks. ONE shared `WEEKLY_LEGACY_POINT_REWARD` constant rather than per-entry amounts, specifically so the system's central guarantee is a single checkable fact: **at most 5 Legacy Points per 7-day window, and only ever via the weekly path.**

**The un-farmability guarantee, and its honest limit.** Three defences, all directly harness-proven: (1) the `completed` flag makes a second grant inside one window impossible — 5,000 further evaluations after a completion granted zero extra; (2) a window's start only ever advances by a full period — a simulated YEAR of instant completions produced 53 grants across 53 windows with **no window shorter than 7.0000 days**; (3) config lookup is **pool-scoped** (`objectiveConfigById` searches only the rotating pool, `periodicObjectiveConfigById` only that kind's pool), which is load-bearing rather than tidy: a single "search every pool" lookup would let a hand-edited save move a weekly id — the only configs carrying `rewardLegacyPoints` — into the fast-rotating `objectives` array and farm LP on a per-minute cycle. The rotating sanitizer drops such an id as unknown, and a cross-pool id in a periodic slot is nulled with its `completed` flag downgraded so it can't present as already-claimed. The honest limit, documented rather than papered over: a player who deliberately advances their device clock can advance windows. That is unavoidable in an offline, client-only game with no server time and no monotonic clock that survives a reload — and it is precisely why the reward is calibrated small enough not to be worth defending with a backend.

**Prestige interaction.** Both slots deliberately SURVIVE `resetForLegacy()` — they are commitments to a period of real time, not to a run, and a player who prestiges on day 3 of a weekly should not lose the week (nor be able to reset an already-claimed weekly by prestiging, which makes this the safe direction as well as the kind one). Only baselines move, and only for run-scoped stats, via `rebaselinePeriodicObjective` — the same correction the rotating array already gets, for the same reason (a prestige zeroes tier state, so a stale baseline would leave the objective permanently unachievable). An already-completed slot is left entirely alone. `resetProgress()`'s dev wipe, by contrast, replaces both with brand-new slots anchored to now, since its documented purpose is a state indistinguishable from a brand-new player's.

**Schema migration v7 → v8** (`dailyObjective`/`weeklyObjective` are genuinely new `partialize` fields — exactly the case this project's versioning convention exists for). `SCHEMA_MIGRATIONS[7]` generates a full valid pair rather than leaving a load-time self-heal to it, with baselines taken from **that save's current stats, never zero** — a veteran save has hundreds of wins and dozens of tier levels banked, and a zero baseline would present both new objectives as already complete and pay them out (Legacy Points included) on the very next tick, for work done long before either tier existed. Both boundaries anchor to the load moment, so a migrating player gets a full fresh day and week rather than an already-expired one. It uses the same defensive shape as `SCHEMA_MIGRATIONS[5]`/`[6]`: tier arrays treated as empty unless already exactly the expected length, the null-tolerant `selectObjectiveStats` kept OUTSIDE the try, and only the throw-prone income-rate call wrapped — an uncaught throw in a migration step is swallowed by zustand's persist hydrate and discards the ENTIRE migration. `merge()` gained `ensurePeriodicObjective` for both slots (a save already AT the current version skips `migrate()` entirely, so `merge()` is the only place a corrupted-but-current slot is ever looked at); it replaces an unusable slot wholesale, nulls a malformed/cross-pool objective while KEEPING the boundary (so a corrupted save can't be a way to skip a weekly's 7-day wait), and re-baselines a stale baseline sitting above the live stat rather than leaving the slot frozen at 0% forever.

**UI.** New sections in the existing card, separated by hairline rules rather than given their own surfaces — they read as sections of one list, not competing panels. Each shows its label, a "Resets in <time>" countdown, and either the standard progress row plus a reward line, or the completed state. Rewards are surfaced for these two tiers but still not for rotating ones: these are once-a-period commitments, and knowing a weekly carries Legacy Points is the whole reason to prioritise it. The LP amount uses the Legacy system's own purple accent (`--color-legacy`) — the one place a Legacy Point figure appears outside Franchise HQ — so it reads instantly as the scarce permanent currency rather than more Revenue. ### Unattended auto-play pause — a managed tier stops after 4 hours untouched

A hard brake on indefinitely-unattended idling: any manager-hired tier that goes **4 hours without a manual interaction** stops auto-ticking until the player interacts with that tier again. Uniform across both sports, per-tier, and completely invisible to manual play.

**Per-tier, never global.** `VentureTierState` (`engine/ventureTiers.ts`) gained `lastInteractionMs` — the epoch ms of the last MANUAL interaction with THAT tier specifically. Interacting with one tier does nothing for any other; a player who keeps clicking The Sunday League while nine other managed tiers idle will find exactly those nine paused and that one still running. Verified directly rather than assumed.

**Explicit-`nowMs` throughout, per this project's own precedent.** `isAutoPlayPaused(tier, nowMs, thresholdMs?)` takes time as a PARAMETER and reads no clock internally — the same pattern the Daily/Weekly objectives work established, and for the same reason: it is what lets the exact 4-hour boundary be asserted at −1ms / exactly at / +1ms instead of waited out. The store passes `Date.now()`; the UI passes a clock from its parent tab; the harness passes whatever instant it likes.

**Threshold: 4 hours — kept as specified, and confirmed rather than assumed.** The number that actually constrains it is the SLOWEST single match anywhere, since a threshold that can interrupt a match a player is plausibly watching would be wrong. Measured against the real `autoTickIntervalMsForTier` and each sport's real match length: soccer tier 10 is the slowest at ~26.0 min/match, so 4h is **~9.2 of those** (and ~267 matches at soccer tier 0, ~923 at baseball tier 0). For contrast a 1h threshold would be only ~2.3 of that slowest match — tight enough that one interrupted check-in could strand a match mid-flight; 8h clears it comfortably too but weakens what the mechanic is for. 4h keeps the intended meaning ("this has been running unattended for a long time") while never being able to interrupt a match in progress for an engaged player. The harness asserts the ≥4-matches-everywhere property directly, so a future pacing change that broke it would fail rather than silently degrade.

**What pausing does, precisely.** The authoritative gate is a single early `return` at the top of `tickTier`/`tickBaseballTier`, taken only when `source === 'auto'`:
- **Nothing runs.** `match`, `tickIndex`, `cumulativeRevenue` are never written, so an in-progress match freezes byte-for-byte — same score, same inning/outs, same tick position. Harness-verified by `JSON.stringify` equality across 50 blocked auto ticks, and live in the browser (a 1-1 match at minute 54 was still 1-1 at minute 54 after five real seconds of the app running).
- **`managerHired` is NOT lost.** The purchase is permanent; only its effect is suspended.
- **Resuming continues from the frozen position**, not from a fresh match — verified as tick 54 → 55 on the resuming click, not 54 → 0.
- No Revenue accrues, so no objective/achievement progress leaks in either.

**Resume: ANY manual interaction with that tier.** A manual tick (`tickTier(id, 'manual')`) and all six purchase actions (`upgradeTier`/`hireManagerForTier`/`unlockTier` and their baseball twins) stamp `lastInteractionMs = Date.now()` on their own tier, which resumes it immediately. Merely having the tier's screen open does nothing — the clock is driven by interaction, not by viewing.

**Manual play is untouched, by construction.** The guard is `source === 'auto' && isAutoPlayPaused(...)`, so a manual tick is never even tested against it. `tickTier` gained a `source: TickSource` parameter defaulting to `'auto'`; the card adapters pass `'manual'` explicitly and `useMatchTicker` passes nothing. This is NOT a fork of the resolution path — CLAUDE.md's manual-before-automated pattern still holds, both callers still run the identical `resolveVentureTierTick`; the parameter exists solely to answer "should this tick be gated, and should it stamp the clock".

**FAIL-OPEN on missing or garbage data — a deliberate direction.** A `0`, negative, or non-finite stamp (and a non-finite `nowMs`, and a rewound clock) all report NOT paused. A brand-new tier is created with `0` and legitimately has no history — but it also has no manager, and `managerHired` can only become true via `hireManagerForTier`, which stamps a real timestamp, so a tier that can actually auto-play always has one. The remaining ways to see garbage here are a hand-edited or partially-corrupted save, where failing CLOSED would silently freeze a player's whole economy with no visible cause, while failing open merely restores the pre-existing always-on behaviour until their next interaction stamps it properly. **Never pause because of bad data.**

**A paused tier still counts toward `tierIncomeRatePerSecond` — KEPT deliberately, and the most-contested call in this session.** Three of the five review lenses raised it independently and a reproducer confirmed the magnitude (a save with every tier paused still reports its full structural rate, and that survives a reload). It is kept anyway:
- **The opposite direction is an actual exploit.** That rate sizes income-scaled objective TARGETS. Excluding paused tiers would mean a player whose tiers all pause overnight — which happens on its own, for free — sees the rate collapse to `OBJECTIVE_FLOOR_INCOME_RATE`, so the daily rolling over at local midnight draws a trivially cheap "Earn N Revenue" target they complete instantly on resuming. Letting the game go idle must never be the optimal way to play it. (One skeptic reached this independently, noting the proposed direction "would reintroduce a bug this project already fixed once" — the same degenerate-target class the Objectives session had to fix with the rate floor.)
- **For rewards it is generous, never exploitable.** Pricing off structural income can only over-pay relative to what a paused player is actually earning, and buying that over-payment costs them all their real income meanwhile.
- **The honest downside is self-correcting by design.** A target drawn while tiers are paused is sized against income not currently being earned, so it reads as too hard until the player resumes — and resuming is one click per tier, which is precisely the behaviour this mechanic exists to elicit.

The tripwire recorded in the code for a future session: if a reward or target is ever derived from this rate in a context where OVER-stating it would benefit a player for doing nothing, that consumer needs its own paused-aware rate — not a change to the shared function, which would reopen the exploit above.

**Where the time actually comes from.** The pause boundary is time-driven, so the set of auto-playing tiers can change with nothing else changing at all. A new exported `useNowMs(intervalMs)` (`hooks/useMatchTicker.ts`, so this project's "setIntervals live in exactly one module" convention still holds) supplies a coarse moving instant; `AUTO_PLAY_PAUSE_CHECK_MS` is 60s, which is far finer than a four-hour threshold needs. Two consumers use it — `useMatchTicker`, which now excludes paused tiers from its interval sets, and each tab, which owns ONE clock for all of its cards rather than one interval per card. `ObjectivesPanel` was switched from its own hand-rolled copy of exactly this to the shared hook, since a second consumer arriving is precisely when two ad-hoc copies start drifting.

Nothing about CORRECTNESS rests on that 60s cadence: the store's own guard is authoritative and needs no clock, so at worst a paused tier's interval fires a few harmless no-ops before the clock catches up. Resuming needs no clock tick at all — a manual interaction changes `lastInteractionMs` in the store, which alone re-runs the selectors and recreates the interval immediately (observed live: auto-play resumed within the same second as the click).

**Display lag is bounded, and the card does NOT claim otherwise.** The card derives its paused flag from the SAME `isAutoPlayPaused` the store's guard uses, so the two can never disagree about the RULE — but they can briefly disagree about the MOMENT: the store reads the clock on every tick, while the card reads its tab's polled `nowMs`. A tier that just crossed the threshold can therefore still render as `AUTO` for up to `AUTO_PLAY_PAUSE_CHECK_MS` before repainting, even though it genuinely stopped advancing the instant it crossed. That constant was retuned from 60s to **15s** so the window is imperceptible against a four-hour threshold. An earlier comment here claimed the two "can never disagree", which adversarial review correctly called out as something a polled clock cannot promise; the comment now states the real guarantee.

A verifying agent then measured the retuned behaviour against the real store and a real `VentureCard` render: a **14-second worst-case lag** (a sawtooth decaying to 0, exactly what a 15s poll produces), with the economy genuinely frozen throughout the window, and — importantly — **zero samples of the reverse direction**, i.e. the card can never show `PAUSED` while the tier is in fact still ticking. It also re-confirmed on that same post-fix code that resume works and manual clicking is unaffected. The lag is therefore bounded, one-directional, and display-only.

**UI.** A paused tier's `AUTO` badge becomes an amber `PAUSED` badge, and the "Manager hired — auto-advancing." line becomes: *"⏸ Auto-play paused — this tier ran 4 hours without you. Your manager and match progress are safe; Push the Attack (or any purchase here) resumes it."* (the action label is the sport's own, so baseball reads its own verb). Amber `--color-warning` — the same "attention needed, nothing is broken" signal this design system already uses for a locked-but-affordable tier — deliberately not a red error tone, because nothing has gone wrong and no progress was lost. The card derives its paused flag from the SAME `isAutoPlayPaused` the store's guard uses, so the message can never disagree with whether the tier is actually advancing.

**The Hub carries a pause signal too** (`⏸ Auto-play paused — N tiers`, amber, on the affected sport's building card, absent entirely when nothing is paused). This goes slightly beyond the letter of the spec, which asked only for a message on the tier — it was added because four independent review lenses converged on the same gap: the Hub is the screen a returning player ALWAYS lands on, and the one moment this mechanic most needs to communicate ("you were away, your economy is stopped") was invisible until they happened to open a sport screen. It reuses the same `isAutoPlayPaused`, per the Hub's own standing shared-derivation rule.

**Schema migration v8 → v9, and the one decision that matters in it.** `lastInteractionMs` is a new field nested inside something already persisted — exactly the case this project's versioning convention exists for. `SCHEMA_MIGRATIONS[8]` stamps **every tier of both sports with the migration moment**, giving each a full fresh 4-hour window starting from that load. The alternative — leaving them unstamped, or back-dating to some notion of "when they were last played" — would mean an existing player opens the app after this update and finds tiers ALREADY paused, complaining about inactivity they never had a chance to avoid; that reads as the update having broken their game, which is the opposite of the mechanic's purpose. There is also no honest data to back-date FROM: no prior save records when a tier was last touched. Note this deliberately writes a REAL timestamp rather than the fail-open `0`, so the pause starts applying normally from that moment on rather than never applying to migrated tiers at all.

**Adversarial review (5 lenses × 2 independent skeptics per finding; 29 verdicts) raised 15 candidates, deduping to 6 distinct issues. Kept with reasoning recorded: (5) the phantom-income property above. Declined: (6) a bulk "resume all tiers" control — that would defeat the mechanic, whose entire point is per-tier manual engagement; the Hub signal addresses the discoverability half of that finding.

**OPEN DESIGN QUESTION, reproduced and deliberately NOT decided unilaterally: closed-app time counts toward the 4-hour threshold.** `isAutoPlayPaused` measures WALL CLOCK since the last interaction, but this game has no offline progress — the ticker only runs while the app is open. So a player who plays in the morning, closes the tab, and returns nine hours later finds every managed tier paused on arrival, despite auto-play having run for none of those hours. A verifying agent reproduced this across two separate Node processes against the real committed code: 4 of 4 managed tiers paused on reopen, **zero** revenue and **zero** tick advancement accrued during the closed gap, and one manual tap required per tier (up to 22 on a developed two-sport save) before passive income resumes.

The two skeptics split, and both are right about facts:
- **Against calling it a bug:** the spec says "4 hours without a manual interaction", which is literally what wall clock measures; nothing is lost (no revenue accrues while closed either way), `managerHired` survives, matches freeze intact, and resume is a free tap. Wall-clock-across-sessions is also this project's established time model — the Daily/Weekly windows roll at local midnight across closed time by design.
- **For calling it a bug:** the mechanic is named for unattended AUTO-PLAY, and nothing was playing. The migration step in this very session went to real lengths to avoid exactly this "already paused, through no fault of mine" arrival experience — but that protection is single-use, while the identical experience becomes the norm on every return after a >4h gap, which for an idle game is the most common play pattern.

A fix would count only app-open time (e.g. a persisted heartbeat, with the closed duration added back to each tier's stamp on load), which means new persisted state and another schema bump. That is a mechanic-level change to a shipped, explicitly-specified behaviour, so it is left for the owner to call rather than reshaped at the end of the session that built it. What WAS fixed immediately is the copy: the card said "this tier ran 4 hours without you", which is simply false when the app was closed, and now reads "no activity on this tier for 4 hours" — true either way.

## Conventions
- Scoped sessions: work one build-order step at a time. Stop and summarize before starting the next step unless explicitly told to continue.
- Prefer clarity/maintainability over premature optimization — this is a solo long-term project, not a performance-critical app.
- Solo git workflow: commit directly to `main` for all build-order steps. Do not create feature branches or open pull requests unless explicitly asked.
- **ALWAYS PUSH, never just commit.** Every session that commits MUST also `git push` to `origin` as part of the same session — pushing is not a separate step that waits to be asked for. This is a standing rule because it was already missed once: a deploy sat **17 commits behind** `origin/main` purely because past sessions committed without pushing and no prompt explicitly said "push." Treat "commit to main" as always meaning "commit AND push to origin." Before ending a session, verify with `git status` that the branch is not ahead of `origin/main`.
- End-of-session deliverables: every session ends with (1) a written summary of what was done, (2) a plain-text description of the current UI state as observed via the browser preview tool (what's rendered, what changed visually) — even without a screenshot, so the user can relay it to another reviewer — and (3) a playable link left running (start/restart the dev server via the browser preview tool, clear `localStorage` for a fresh-player state, then give the `http://localhost:5173` URL — noting it's local-only and stops when the session ends). Don't stop the server as a "cleanup" step; leave it running and reset instead.

## Testing Conventions
Verification depth should scale with the risk of the area being touched, not be applied uniformly — this is a standing rule for how future sessions should calibrate their own effort, not something that needs to be re-specified in every prompt.

- **Cosmetic/presentational-only changes** (styling, copy, renames, layout, icon swaps) — build + lint + a basic browser confirmation that the change renders as intended is enough. Don't reach for harnesses or adversarial review for a color swap.
- **Changes touching store logic, economy/payout calculations, match-resolution, prestige, or save/schema/persistence** — these get the full adversarial/dual-verification treatment: a direct-import Node harness exercising the real functions (not a reimplementation) covering the normal path AND edge cases (fresh state, mid-transition, boundary/saturation cases, legacy/migrated save shapes), plus an adversarial review pass (a workflow, or at minimum an independent agent/self-review explicitly hunting for ways the change could be wrong) before calling it done.
- **Why these specific areas:** this project's own history is the evidence, not a hypothetical — schema/migration bugs (ninth, fourteenth, fifteenth amendments), a hidden-tier-reveal exploit via hand-edited flags (ninth), a getPerformanceFactor bonus-leak that silently overpaid a downgraded outcome (thirteenth), the SAME class of leak reopened by an unrelated cosmetic change two sessions later (fifteenth), and a notification-crash/non-array-tiers-crash pair introduced by a well-intentioned refactor (fourteenth, fifteenth) — every one of these was in exactly the areas called out above, and every one shipped once before an adversarial pass caught it. Cosmetic-only sessions in this same history (sixth, tenth amendments) have never produced an equivalent incident.
- **When a single session mixes risk levels** (e.g. one cosmetic change alongside one store-logic change), calibrate per change, not for the session as a whole — a low-risk change bundled alongside a high-risk one doesn't need the heavy treatment just because they shipped together, and a high-risk change doesn't get to skip it just because most of the session was cosmetic.
- **Full multi-agent Workflow-tool review is not the only way to satisfy the "high-risk" bar** — it's the deepest option, appropriate when the user has opted into multi-agent orchestration or the change is large/tangled enough to warrant it. A direct-import Node harness plus a single independent adversarial review pass (self-review or one agent explicitly trying to refute the implementation) is a legitimate, lighter-weight way to satisfy the same "don't skip verification on high-risk areas" principle when a full workflow isn't warranted or requested.
